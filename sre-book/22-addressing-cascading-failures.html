Addressing Cascading Failures

A cascading failure is positive feedback in a distributed system: one failure increases load or latency elsewhere, causing additional failures, which further increase the pressure. The chapter explains the resource feedback loops that create cascades and the concrete controls—load shedding, deadlines, bounded queues, backoff, capacity headroom, isolation, and overload testing—that stop them.

01 — cascade

How a small failure becomes a large one

The book defines cascading failure as a failure that grows over time because the failure itself makes more failure likely. A classic example is losing one replica, which moves its traffic to surviving replicas. If the survivors have insufficient headroom, they become overloaded and fail too.

In the Shakespeare example, cluster A normally handles about 1,000 QPS. After another cluster fails, A is asked to handle about 1,200 QPS. Instead of simply serving 1,000 and rejecting 200 cleanly, resource exhaustion can make its successful throughput fall below the previous 1,000 QPS.

That distinction is central. A well-behaved overloaded service reaches a plateau of useful work. A cascading service experiences a falling useful-throughput curve as extra offered load destroys the capacity it still had.

Illustrative chapter sequence: A is healthy at ~1,000 QPS. Failover raises offered load to ~1,200 QPS. If overload causes crashes or deadline misses, useful throughput can fall below 1,000 QPS—so 200 extra QPS can destroy more than 200 QPS of service.
02 — resources

Resource exhaustion feeds on itself

CPU, memory, threads, file descriptors, queue capacity, and caches are not independent. Exhausting one resource often increases pressure on another.

The chapter's Java example is a useful causal chain: poorly tuned GC consumes CPU → requests finish more slowly → more requests remain in progress → RAM usage increases → less RAM is available for cache → cache hit rate falls → more backend RPCs are issued → backends run out of CPU or threads → health checks fail.

This produces the classic GC death spiral: less CPU causes slower requests and more live state, which increases GC pressure and removes still more CPU.

During an incident, secondary symptoms can therefore look like primary causes. The backend crash may be real, but its initiating cause can be an upstream cache collapse.

03 — crash loops

Why returning below the original traffic level may not recover the system

Once several tasks have crashed, the fleet has less capacity than before the overload. Newly restarted tasks may immediately receive a flood of queued or retried traffic and crash again.

The chapter gives the intuition that a service healthy at 10,000 QPS but entering a cascade around 11,000 QPS may not recover merely by lowering traffic to 9,000 QPS. With much of the fleet unhealthy, 9,000 QPS can still be far above the reduced fleet's instantaneous capacity.

Recovery often requires a much more aggressive load reduction—sometimes almost a complete drain—until enough replicas are healthy, caches are warm, retries have subsided, and capacity is restored.

Recovery principle: the load needed to recover can be much lower than the load that the healthy fleet can sustain.
04 — retries

Retries are a positive-feedback mechanism unless controlled

Automatic retries improve reliability for isolated transient failures, but during broad overload they generate new demand precisely when capacity is lowest.

The chapter walks through a retry wave in which 100 QPS of retries becomes 200, then 300, while fewer original requests succeed. The backend spends CPU, memory and file descriptors on requests that will eventually fail, then crashes and shifts its traffic to the remaining tasks.

Even after original traffic returns to its pre-incident level, retry traffic can keep the service overloaded.

Use randomized exponential backoff, add jitter so clients do not synchronize, and bound retries. For wide failures, stop retries entirely or return an error that communicates that retry is not useful.

05 — deadlines and queues

Bound the amount of useless work

Every request should have a deadline that represents how long the caller still cares about the result. Work should not continue indefinitely after the user or upstream caller has timed out.

Unbounded queues turn overload into latency. A queue can make a service appear to accept requests even though it has merely postponed their failure; queued requests also consume memory and can make recovery slower.

Reject work early once the system crosses a safe concurrency/queue threshold. This keeps resource use bounded and gives clients a chance to degrade, back off, or redirect.

06 — preserve headroom

Capacity planning must include failure modes

Capacity planning for normal peak traffic is insufficient if the service must survive a cluster, zone, machine group, or dependency failure.

Planned drains and maintenance can produce the same load redistribution as unexpected failures. A dependency being drained may also force traffic to a distant site and raise latency.

Traffic profiles change too: a frontend change may make each request more expensive even if QPS is unchanged. Organic user data growth can increase payload size.

Do not count opportunistic slack CPU from other jobs as guaranteed capacity. The chapter warns that resource overcommit can make apparent headroom disappear suddenly when another workload uses the shared slack.

07 — test beyond failure

You need to know the shape of overload before production discovers it

The chapter recommends load testing until the component fails—and continuing beyond the initial failure point.

A healthy overload curve should show successful throughput increasing until capacity is reached, then roughly flattening while errors/degraded responses rise. A dangerous curve shows successful throughput declining as offered load continues upward.

Test with realistic dependencies, failure modes, reduced capacity, cache states, request mixes, and retry behavior. The exact cascade path is difficult to predict from first principles, so empirical overload testing is essential.

Run tests within committed resources rather than relying on borrowed cluster slack, otherwise the test may certify capacity the service does not truly own.

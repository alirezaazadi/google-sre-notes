Google Site Reliability Engineering Book · Chapter 7

The Evolution of Automation at Google

Automation is a force multiplier, not a goal by itself. The chapter traces a maturity path from manual operations through scripts and generic platforms toward systems that directly maintain their own desired state, while emphasizing consistency, faster repair, observability, and the dangers of leaky abstractions.

01 — value

Why automate besides scale?

Humans executing a repeated procedure hundreds of times will not do it identically every time. Automation's first value is consistency: one implementation of the procedure can be tested and executed repeatedly.

A well-designed automation platform also centralizes fixes, becomes reusable infrastructure, runs more frequently than humans could, and emits metrics about the process itself. For common faults, automatic detection/repair can reduce MTTR substantially.

02 — platform

Automation can become a common control plane

Google's relatively uniform infrastructure and willingness to build APIs make broad automation feasible. Instead of solving one operation with a local shell script, a platform can expose high-level operations consistently across many services.

This is “software that acts on software.” Typical cases include account creation, cluster turnup/turndown, installation/decommissioning, software rollout, runtime configuration, and dependency changes.

03 — abstraction

Higher-level automation is easier—until the abstraction leaks

A rollout abstraction may promise “old version or new version,” but real failures include network partition mid-rollout, failed machines, staged-but-not-restarted binaries, partially restarted tasks, and unknown verification state. Automation has to model these intermediate states or stop safely and ask for intervention.

A generic abstraction that silently assumes atomicity can fail systemically across every service that trusts it. This is why understanding the real state machine matters even when the operator interface is high level.

04 — hierarchy

The five-step automation maturity path

The hierarchy expresses a preference for pushing reliable control closer to the system that owns the relevant state. External glue tends to bit-rot when the product changes because its lifecycle and priorities are separate.

Infrequently executed emergency automation is especially dangerous: failover might run only every few months, so incompatibilities can accumulate unnoticed. Practice and continuous validation are necessary.

05 — not everything

Automation can magnify mistakes

Automating the wrong operation can perform damage much faster and over a much larger fleet. Good automation therefore includes bounds, validation, observability, idempotent/reconciling behavior where possible, staged execution, and a clear failure state.

The best outcome can be a design that removes the operation entirely. An autonomous system is better than a perfect runbook-executing robot when the system itself has enough information to maintain the invariant safely.

06 — design question

What belongs inside the system?

Ask which decisions require knowledge that the service itself already has—replica health, desired count, current leader, configuration version. Those are strong candidates for internal control loops.

Leave human judgment for ambiguous policy, unusual risk, or business decisions. SRE's goal is not to automate responsibility away; it is to stop using human attention for mechanical state convergence.

07 — value

Automation pays in more currencies than engineer minutes

The chapter identifies several independent reasons to automate. Consistency removes the natural variation of humans repeating a procedure hundreds of times. Platform leverage turns one implementation into something reusable and measurable. Faster repair reduces MTTR for common faults. Faster action lets machines perform well-defined failover or traffic switching before a human could react. And time savings accrue across every future operator who would otherwise perform the task.

This wider view changes the cost/benefit calculation. Even if writing an automation takes roughly as long as the first several manual executions, it may still be worthwhile because it standardizes the operation, creates telemetry, prevents drift, and decouples the person performing the operation from the person who originally understood it.

08 — bit rot

Rarely used external automation is especially fragile

A subtle problem is that automation maintained outside the system can drift away from the system it controls. Turnup or failover scripts may be executed only every few months, so the feedback cycle is long. Meanwhile, the service evolves and the script does not.

This motivates the hierarchy described in the chapter: manual operation → system-specific external script → generic external automation → automation shipped and maintained with the system → a system that detects the condition and handles it automatically.

The final stage is preferable because it removes a separate piece of glue code and its independent lifecycle. The deeper SRE goal is therefore not 'automate every runbook'; it is to design services whose normal failure handling is intrinsic.

Highest level: if the database can notice that its leader failed and safely elect/fail over by itself, an external operator or failover script is no longer part of the normal path.

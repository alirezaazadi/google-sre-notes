Appendix B — A Collection of Best Practices for Production Services

This appendix is not a random checklist; it is a compact set of production invariants learned from real failures. The themes are fail safely on bad inputs, roll out progressively, define reliability like a user, use error budgets, make monitoring actionable, and design every operational mechanism so one bad change does not become a global outage.

01 — fail sanely

Reject bad configuration without destroying the working state

Validate configuration syntax and semantics, detect empty/truncated inputs, and alert on implausible changes such as dramatic size differences.

When new data looks invalid, prefer continuing with the last known-good configuration while requesting human review.

The appendix gives two memorable failures. In 2005, an empty DNS entry file was accepted and Google properties returned NXDOMAIN for about six minutes. In 2009, a valid but incorrect suspect-URL file containing only '/' caused every URL to match as malware.

Both failures are examples of why syntactic validity is not enough: systems need sanity checks based on expected semantics and magnitude of change.

02 — rollout

Configuration and binaries both deserve progressive rollout

Nonemergency changes should move through stages, with the fraction and dwell time chosen according to service size and risk.

Different geographies can expose diurnal and traffic-mix differences.

Rollouts must be supervised by an engineer or a monitoring system proven reliable enough to decide health. If unexpected behavior appears, the recommendation is to roll back first and diagnose afterward to minimize MTTR.

03 — SLO

Measure reliability where the user feels it

Server-side success can overstate experience if DNS, networks, clients, rendering or protocol layers fail outside the measurement point.

The appendix notes that moving Gmail assessment closer to client experience produced a lower measured availability and drove client/server changes that improved reliability from roughly 99.0% to over 99.9% over time.

The lesson is not the product number itself; it is that measuring closer to the user can expose reliability work hidden by internal metrics.

04 — error budget

Let one metric align product and SRE

Error budget is simply 1 − SLO over the chosen window. While budget remains, teams can take reasonable launch/change risk. When it is exhausted, change freezes except urgent security and reliability fixes until the budget recovers or resets.

For very high SLOs, longer windows such as a quarter can be more meaningful because monthly allowable failure time becomes tiny.

Error budgets turn a recurring organizational argument—'ship or stabilize?'—into a data-driven policy.

05 — monitoring

Only three monitoring outputs need humans

Page: a human must act now. Ticket: a human must act within days. Log: retain information for later analysis but no immediate human action.

Important alerts sent to email without explicit ownership/action become the moral equivalent of /dev/null because human vigilance eventually fails.

Monitoring must therefore be designed around action, not around how many abnormalities the system can detect.

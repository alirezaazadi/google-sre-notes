Handling Overload

Load balancing can distribute work, but it cannot create capacity. This chapter explains how a serving system should behave once demand exceeds available resources: measure the true cost of requests, isolate customers with quotas, make clients throttle themselves, propagate request criticality, protect each task locally, and keep retries from multiplying the overload.

01 — degrade, don't collapse

What overload handling is trying to achieve

Even an excellent load-balancing policy eventually encounters a point where some resource becomes saturated. The desired behavior is not “continue accepting everything until the process crashes.” A reliable service should keep doing as much useful work as its capacity allows and reject or degrade the excess work cheaply.

The chapter starts with graceful degradation. A search system might search only a fraction of its corpus; a service might use a slightly stale local copy instead of consulting expensive canonical storage. Degraded answers preserve some user value while requiring less computation.

If even degraded work is too expensive, errors are unavoidable. The important design question becomes: which requests fail, how cheaply do they fail, and how do clients react?

Simple capacity bound from the chapter: 100 backend tasks × 500 requests/s/task = 50,000 requests/s. A global load balancer should not intentionally route more than that nominal capacity to the datacenter—but local imbalance and variable request cost can still overload individual tasks.
Goal: under excess demand, a backend should continue serving near its useful capacity rather than becoming slower and slower until its useful throughput collapses.
02 — QPS trap

Why queries-per-second is a weak capacity metric

Different requests can cost radically different amounts of CPU, memory, I/O, fan-out, or downstream work. Their cost can change as software evolves or traffic mix changes. A static proxy such as “keys read per request” can therefore become wrong even if it once correlated with resource use.

Google often models the normalized cost of a request from the CPU time it actually consumes. CPU is frequently a useful primary provisioning signal because garbage-collection pressure and many other costs eventually appear as CPU load. Where memory, disk, or another resource can exhaust first, those resources must be modeled separately.

This is a general systems lesson: capacity is a property of a workload on a specific implementation, not merely a request count.

Common failure: declaring a service capable of “20k QPS” without stating the request mix, latency target, or limiting resources. The number can become meaningless after one feature changes request cost.
03 — customers

Per-customer quotas isolate overload

Global overload often occurs because many independent clients cannot perfectly coordinate launches and growth. If one client suddenly sends far more work than negotiated, unrelated clients should not lose service.

The chapter therefore uses per-customer resource quotas, expressed in a resource such as CPU-seconds per second. The example backend has 10,000 CPUs globally, while individual customer quotas include Gmail 4,000, Calendar 4,000, Android 3,000, Google+ 2,000, and other users 500.

Those quotas intentionally sum to more than physical capacity. This is analogous to statistical multiplexing: the owner assumes all clients will not hit their maxima simultaneously. The important point is that each client has a defined boundary when the system must decide whom to reject.

Effective limits are pushed down to individual backend tasks using aggregated usage information, which requires the infrastructure to attribute resource consumption to each request.

Example quota arithmetic: physical capacity = 10,000 CPU-seconds/s. Listed maximum quotas can total >10,000 because they are not expected to peak simultaneously. If Gmail is consuming its 4,000 allocation while another client exceeds its own quota, quota enforcement protects Gmail even during global pressure.
04 — throttle

Why the client should sometimes reject its own requests

Rejecting work at a backend is cheaper than fully processing it—but not free. For very cheap operations, protocol parsing and connection handling can cost almost as much as the real request. A sufficiently overloaded backend can therefore spend most of its CPU merely rejecting traffic.

Google's adaptive client-side throttling keeps recent counts of application-layer requests and backend accepts. As accepts fall below requests, the client increasingly rejects new work locally before it reaches the network.

The aggressiveness is controlled by a multiplier K. The chapter discusses a commonly preferred value near 2, which allows enough traffic through to detect backend recovery quickly. A much more aggressive value such as 1.1 would cause only about one backend rejection per ten accepted requests, but would propagate recovery information more slowly.

The design is appealing because each client uses only local history—no new coordination service or RPC is required.

Key trade-off: send enough probe traffic that clients notice recovery quickly, but not so much rejected traffic that the backend wastes its remaining capacity saying “no.”
05 — criticality

Keep important requests when everything cannot fit

Not all traffic has equal value. Google models four request criticalities: CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS, and SHEDDABLE.

Production user-visible work is normally CRITICAL, while the highest-impact paths may use CRITICAL_PLUS. Batch work is generally SHEDDABLE_PLUS, and traffic that tolerates frequent partial loss can be SHEDDABLE.

When a customer is over quota or a task is overloaded, lower-criticality work is rejected before higher-criticality work. Criticality is propagated automatically through RPCs so a downstream service deep in the call graph sees the original importance of the user request.

Criticality is deliberately separate from latency sensitivity. Autocomplete suggestions may be very latency-sensitive yet highly sheddable: missing one suggestion is preferable to allowing optional work to damage the search result itself.

CriticalityMeaning under pressure
CRITICAL_PLUSFailure causes especially serious user-visible impact; shed last.
CRITICALNormal production user-visible traffic; capacity should cover expected load.
SHEDDABLE_PLUSPartial unavailability is expected; common for batch work.
SHEDDABLECan tolerate frequent partial and occasional full unavailability; shed first.
06 — local defense

Utilization signals protect individual tasks

Global quota and load-balancing state is always delayed. Therefore every backend task must be able to protect itself using local utilization signals.

CPU utilization is common, but Google also uses an executor load average: count active or runnable threads, smooth the signal with exponential decay, and start rejecting requests when sustained runnable work exceeds available processors.

Short bursts are mostly absorbed by the smoothing function, while sustained pressure triggers shedding. Memory pressure or multiple combined resource signals can be added for services whose limits are not CPU-dominated.

Higher criticality can use higher rejection thresholds so optional work disappears before critical work.

Design invariant from the chapter: an individual task provisioned for a certain useful rate should continue serving roughly that rate even if it is offered substantially more traffic. Excess input should cause controlled rejection, not a crash.
07 — retries

Retry only when another backend probably has spare capacity

A task-level overload error can mean two very different things. If only a few tasks are hot, an immediate retry may naturally land on a healthier backend and act like organic load balancing. If most of the datacenter is overloaded, retrying only increases the problem.

The chapter uses a per-request maximum of three attempts and a per-client retry budget that limits retries to roughly 10% of requests.

Without the per-client budget, the worst case can grow request load to just under 3× the original offered traffic because each request may be attempted multiple times. With the 10% client retry budget, the normal amplification is constrained to about 1.1×.

Backends can also inspect histograms of attempt counters. If many requests arriving already have retry attempts, that is evidence of widespread overload; the backend can return an explicit “overloaded; don't retry” response.

In a deep dependency stack, only the layer immediately above the failing dependency should retry. If every layer retries independently, retries multiply combinatorially.

Retry amplification: original offered load = X. Up to 3 attempts can approach ~3X in a severe failure. Limiting retries to 10% of client traffic bounds normal amplification to ~1.1X. In a multi-layer stack, independent retries at every layer can be far worse, so retry ownership must be explicit.
08 — connections

Connections themselves consume capacity

Request processing is not the only source of backend load. Large connection pools consume CPU and memory even when QPS is low, and health checking thousands of mostly idle clients can cost more than serving their real traffic.

Large batch jobs can also create connection storms when many workers start simultaneously. The chapter suggests exposing this utilization to cross-datacenter balancing or inserting batch proxy tasks that act as a fuse between a huge batch fleet and shared backends.

The proxy reduces the number of backend connections and lets the batch-specific layer absorb the startup shock instead of destabilizing higher-priority serving traffic.

Effective Troubleshooting

Troubleshooting is a learnable application of the scientific method. Start with a precise problem report, understand normal system behavior, inspect telemetry, generate probable hypotheses, seek confirming and disconfirming evidence, make controlled tests, mitigate safely, and only then turn the finding into a permanent correction.

01 — theory

Troubleshooting is hypothesis-driven

The chapter describes the process as the hypothetico-deductive method. Observations plus a model of how the system should work produce candidate causes. Each cause implies predictions; evidence or a controlled intervention tests those predictions. The result updates the hypothesis set.

Generic troubleshooting skill is valuable, but deep system knowledge makes it dramatically faster. An engineer who understands request flow, dependencies, common failure modes, and telemetry semantics can form better hypotheses earlier.

02 — triage

First determine what is actually broken

Clarify the report: which users, operations, regions, versions, and time range are affected? Verify the symptom independently where possible. Determine severity and whether mitigation is needed immediately.

Do not let the initial report define the entire investigation. “Database is slow” may be the reporter's interpretation rather than the actual failure. Separate observations from conclusions.

03 — examine

Telemetry only helps if you understand its meaning

Logs, metrics, traces, and state snapshots reveal the current system, but irrelevant or misunderstood metrics cause wild-goose chases. A counter that drops can mean less demand, broken instrumentation, or upstream rejection; the name alone is not enough.

Compare affected and unaffected populations: region, instance version, request type, user cohort, dependency, machine class. Differential evidence often reduces the hypothesis set faster than staring at one global dashboard.

04 — diagnose

Rank likely causes; search for disproof

The chapter warns against exotic theories when ordinary causes fit (“horses, not zebras”), anchoring on a previous incident, and treating correlation as causation. Packet loss and disk failures may correlate because both share a power event; neither caused the other.

A strong hypothesis should be falsifiable: ask what observation would make you abandon it. Searching only for confirming evidence allows almost any story to survive.

05 — test

A production change is an experiment with risk

You can test hypotheses passively by comparing evidence or actively by changing one controlled variable. Active treatment is powerful but dangerous: changing several things at once destroys interpretability and may worsen the outage.

Prefer low-risk reversible tests. If a safe rollback or traffic drain mitigates user impact, take it even before full root-cause certainty; restoring service and proving the deepest cause are different objectives.

06 — example method

A concrete debugging walkthrough

Imagine a web API whose p99 latency jumps from 180 ms to 2.4 s while QPS is stable. First verify the client-visible symptom. Break down latency by endpoint and region. Suppose only write requests in one region are slow; CPU is normal, but DB RPC latency and connection-pool queue time are high.

Hypothesis A: database service is overloaded. Prediction: DB-side latency/utilization should also be high. Hypothesis B: network path from API to DB is degraded. Prediction: API-observed DB latency is high while DB processing latency remains normal. Comparing both sides can distinguish them without random restarts.

If draining the affected API cell to another DB path immediately restores user latency, that is strong evidence and a mitigation—but the post-incident work still needs to identify the network or routing failure that made the path slow.

07 — pitfalls

Failure modes of the investigator

  • Irrelevant symptoms: treating every unusual graph as causal.
  • Unsafe testing: changing the system without understanding the effect/blast radius.
  • Improbable stories: skipping common failure modes for a clever theory.
  • Anchoring: assuming today's incident is the same as last month's.
  • Spurious correlation: two metrics move together because of a third cause.
  • Premature closure: symptom disappeared, therefore guessed cause must have been correct.
Interview mindset: say what evidence you would collect and what each hypothesis predicts. That is stronger than listing commands.

Simplicity

SRE treats simplicity as a reliability property. Production systems must change, so the objective is not frozen stability; it is enough simplicity that engineers can change, test, understand, and recover the system without surprises.

01 — balance

Stability without change is not a useful production strategy

A software system could become more stable by never changing code, hardware, dependencies, or user load—but then it would stop being a useful evolving product. SRE's job is to balance agility and stability, using reliable engineering processes so changes remain possible without making production chaotic.

Exploratory code can legitimately trade stability for learning when it has an explicit short shelf life. Production code has a different contract because it must remain understandable and operable for years.

02 — boring

Predictability is a feature

The chapter celebrates “boring” software: code should follow the script and accomplish its intended business behavior without surprising operators. Surprise increases debugging time and failure risk.

Fred Brooks's distinction between essential complexity and accidental complexity is central. Essential complexity belongs to the problem itself; accidental complexity is introduced by our implementation and can often be engineered away.

03 — delete

Every unnecessary line is future risk

Engineers often resist deleting code “in case we need it later,” preferring commented blocks or permanently disabled flags. Source control already preserves history; leaving dead paths in the active system increases distraction and can create dormant failure modes.

The chapter points to incidents such as Knight Capital as a warning about obsolete code paths. A smaller codebase is easier to understand, test, and reason about. “Negative lines of code” can therefore be a meaningful engineering win.

04 — APIs

Complexity can be moved, not removed

A generic central abstraction may look small while forcing every caller to implement conventions, validation, and edge cases. Evaluate simplicity across the whole interaction, including users, clients, operators, deployment, and failure recovery.

Narrow, explicit interfaces make illegal or surprising behaviors harder to express and help teams evolve components independently.

05 — operational

SRE should push back on accidental complexity

When onboarding a service or reviewing a design, SRE has a responsibility to challenge extra modes, unnecessary dependencies, flags, special cases, and overly clever machinery. Those costs are paid later by the on-caller who must reason under pressure.

Simplicity is not minimal feature count. It is the smallest understandable system that satisfies the real requirements, including reliability and evolvability.

06 — essential vs accidental

Not all complexity is removable, but accidental complexity should be attacked

The chapter borrows the distinction between essential complexity—complexity inherent in the problem—and accidental complexity introduced by our implementation choices. Serving web pages quickly has inherent complexity; dealing with avoidable interactions created by an unnecessary framework, mode, or layer is accidental complexity.

SRE should actively push back when new accidental complexity is introduced and should simplify systems it inherits. This is not aesthetic minimalism. Every additional state and dependency becomes something an on-caller may have to understand under pressure.

07 — minimal interfaces

Minimal APIs and modularity make change safer

A minimal API offers fewer methods and arguments, so its semantics can be understood and tested more thoroughly. Refusing to support unrelated use cases can make the supported core substantially more reliable.

Modularity applies the same idea at distributed-system scale: binaries should have clear responsibilities and loose coupling. API versioning allows components to change on different release cadences instead of forcing a synchronized whole-system push.

The chapter applies simplicity to releases too. If 100 unrelated changes ship together and performance regresses, attribution is difficult. Smaller release batches make each change easier to measure, reason about, and reverse.

Useful mental model: source control is the archive. Keeping dead code commented out or permanently disabled behind flags adds cognitive and operational surface without providing a real recovery benefit.

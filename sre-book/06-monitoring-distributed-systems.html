Monitoring Distributed Systems

Monitoring must tell operators both what is broken from the user's perspective and provide evidence for why. The chapter develops black-box versus white-box monitoring, the four golden signals, actionable alerting, and simple monitoring design for rapidly changing distributed systems.

01 — vocabulary

What the monitoring system is doing

Monitoring is collection, processing, aggregation, and display of real-time quantitative system data. White-box monitoring uses internals such as service metrics/logs; black-box monitoring tests externally visible behavior as a user would experience it.

A dashboard summarizes important service state. An alert is a human notification and may go to a ticket queue, email, or pager depending on urgency. The chapter's definitions matter because mixing those outputs is a common source of noisy operations.

02 — why

Monitoring has more jobs than paging

Monitoring supports long-term trend analysis, experiment comparison, alerting, dashboards, and retrospective debugging. Capacity planning and traffic prediction can tolerate more complex/fragile analyses than the pager path.

The critical path from user failure → monitoring → page → human triage should be simple and understandable. Google reports limited success with elaborate dependency-aware alert hierarchies because infrastructure is continuously refactored and those models become stale.

03 — symptom vs cause

Page on what is broken; debug why

“Users receive errors” is a symptom. “Database refuses connections” is a cause. A cause at one layer can be a symptom to the team operating that dependency. Keeping the distinction clear helps minimize noise.

Black-box monitoring is naturally symptom-oriented and strong for paging active user problems. White-box monitoring can reveal imminent saturation, masked failures, and the detailed evidence needed to identify the cause.

SymptomPossible cause
HTTP errorsbackend/database refusing connections
Slow responsesCPU saturation or network loss
One region cannot fetch contentrouting/CDN failure
Private data exposedbad software/config push changed access controls
04 — golden signals

If you measure only four things

Latency: service time. Separate successful and failed request latency; a fast 500 error should not make a service look fast.

Traffic: demand in a service-appropriate unit—HTTP requests, concurrent streams, storage operations, and so on.

Errors: explicit protocol failures, implicit wrong results, and policy failures such as requests exceeding an agreed deadline.

Saturation: how full the constrained resources are. Many systems degrade before 100% utilization, and high tail latency can be an early signal.

05 — alerting

A human page must imply an action

Do not alert because a metric merely looks unusual. The system should either handle the condition automatically or notify a human because an important action is needed. Single-machine failures in a large replicated fleet are typically too noisy and should be absorbed by the architecture.

Simple alerts are easier to reason about during an incident. They should represent a clear failure and link to enough context for basic triage.

06 — worked example

Why latency distributions and error classification matter

Suppose in one minute:
9,900 successful requests average 180 ms
100 failed requests return in 10 ms.
Naive overall average ≈ (9,900×180 + 100×10) / 10,000 ≈ 178.3 ms.
That small improvement over 180 ms is meaningless—the 1% failure rate is a much more important signal. Track success/error latency separately.
Monitoring principle: a useful graph preserves the semantics needed for decisions; aggregation that mixes success and failure can make the service look healthier.
07 — monitoring is engineering

The monitoring system is itself a production system

The chapter warns against treating monitoring as a few dashboards added at the end of development. Even with common infrastructure already available, a Google SRE team of roughly 10–12 people historically often had one, sometimes two, engineers whose primary assignment involved building and maintaining service monitoring.

The critical path from a service problem to a page, then to triage and deep debugging, should be deliberately simple. Complex learned thresholds or elaborate dependency trees can be attractive, but if responders cannot understand why an alert fired, the monitoring system becomes another distributed system to debug during the outage.

Google therefore favors simple, robust paging rules and richer tools for retrospective analysis. Complex analytics may be appropriate for capacity planning or long-term experiments, where an occasional missed data point is tolerable; the pager path has a much stricter reliability and comprehensibility requirement.

Design rule: the more directly a monitoring path can wake a human, the simpler and more robust that path should be.
08 — layers

One team’s symptom is another team’s cause

In a multilayer service, the distinction between symptom and cause depends on where you stand. Slow database reads are the database team’s symptom, but they may be the frontend team’s cause for a slow website. That is why both black-box and white-box views are needed.

For paging, black-box monitoring is powerful because it forces the alert to represent a real user-visible problem that is happening now. White-box metrics are indispensable for detecting masked or imminent problems and for explaining what is happening inside the service.

When debugging a slow frontend, compare how the frontend perceives the database with how the database perceives itself. If the frontend observes high database latency while the database reports normal latency, the network or client-side path becomes a stronger hypothesis than the database server itself.

Google Site Reliability Engineering Book · Chapter 25

Data Processing Pipelines

This chapter studies the operational weaknesses of periodic Big Data pipelines and presents Google's Workflow architecture as a continuous, stateful alternative. The key themes are uneven work, startup and scheduling delay, overlapping executions, monitoring gaps, thundering herds, exactly-once work, leases, immutable task identities, and cross-datacenter continuity.

01 — pipeline depth

From one transformation to deep multiphase systems

A data pipeline reads data, transforms it, and produces new data. Big Data systems commonly chain many such programs, so the output of one phase becomes the input to the next.

The number of chained programs is the pipeline depth. Deep pipelines can contain tens or hundreds of distinct phases.

Periodic pipelines built with systems such as MapReduce are useful, but Google observed that a pipeline carefully tuned at installation tends to become fragile as data volume, customer mix, deadlines and resource availability change.

02 — skew

The slowest chunk determines completion time

Parallel processing works best when work partitions are roughly equal. Real data is often skewed: if data is partitioned by customer, one customer can be orders of magnitude larger than others.

When a stage must wait for all chunks before proceeding, end-to-end runtime is bounded by the worst chunk.

A tempting response to a hanging chunk is to kill and restart the entire phase. Without checkpointing, that discards all completed work and consumes more cluster capacity—the operational response can amplify the original problem.

03 — periodicity

Shorter scheduling intervals eventually stop improving freshness

Batch jobs often run at lower priority and fill spare cluster resources, so startup latency can be open-ended when production work is busy.

As a periodic pipeline is scheduled more often, eventually the next invocation arrives before the previous one can reliably start and finish.

The chapter's example shows that a roughly 20-minute job may become unstable when the configured interval drops much below about 40 minutes because scheduling delays and execution begin to overlap.

At that point, increasing frequency can create queued runs or even preempt nearly finished work instead of producing fresher output.

Key insight: a periodic architecture has a practical latency floor. If business requirements demand continuous freshness, shrinking the cron interval is often the wrong architecture change.
04 — operational patterns

Monitoring gaps, thundering herds, and Moiré load

Periodic jobs are often instrumented to report statistics only when they finish. That is exactly when operators most need live information: a long-running job can hang or fail before final statistics appear.

Large periodic pipelines also start thousands of workers together, producing thundering-herd pressure on the cluster scheduler, shared storage and network.

Multiple independent periodic pipelines can occasionally align their peaks. The chapter calls the resulting interference a Moiré load pattern: each pipeline appears acceptable alone, but their combined periodic peaks produce recurring on-call pain.

Adding more workers blindly can worsen both phenomena.

05 — Workflow

Task Master + stateless workers

Google's Workflow system was designed for continuous processing at scale. The chapter loosely maps it to model-view-controller: the Task Master holds authoritative pipeline state, workers are stateless executors that observe and update that state, and optional controllers perform scaling, snapshotting, rollback or global control.

The Task Master keeps job state in memory for speed while synchronously journaling mutations. Large input/output data is normally stored externally; the Task Master holds pointers to work rather than every data byte.

Workers can disappear at any time. Their replaceability is what lets execution scale independently from durable pipeline state.

06 — correctness

Four layers prevent stale or orphaned work from corrupting output

Work units are uniquely identified and acquired with leases. A worker may commit only while it still owns the current lease.

Each worker writes to a unique output filename, so an orphaned worker cannot overwrite the valid worker's output.

Tasks and configuration are versioned/immutable. If configuration changes while work is in flight, work computed against the old configuration cannot commit.

A unique Task Master server token is also checked on operations, preventing a misconfigured client or load balancer from accidentally talking to an unrelated Task Master with colliding task IDs.

Together these mechanisms give correctness based on current configuration, current lease ownership, unique output identity, and correct master identity.

07 — business continuity

How continuous work survives datacenter failure

Continuous pipelines may need to survive fiber cuts, weather and site failures. Workflow stores global journal/reference state in strongly consistent systems and uses a distributed lock service to identify the writer.

Because globally consistent storage is not optimized for high-throughput local pipeline data, the design uses multiple local Workflows plus a global representation of reference tasks.

As local tasks start, corresponding reference tasks are created globally; when work finishes, those references are removed transactionally. If the global state is temporarily unavailable, local progress blocks rather than violating correctness.

Heartbeat/reference state lets a remote Workflow take over unfinished work after site failure.

Service Level Objectives

This chapter builds the basic SRE language of SLI, SLO, and SLA and shows how to choose meaningful service measures. The central idea is that operational decisions require explicit definitions of what users care about, what is measured, and what range counts as acceptable.

01 — terminology

SLI, SLO, SLA

An SLI is a carefully defined quantitative measure of service behavior. Common examples are latency, error rate, throughput, availability/yield, and durability for storage.

An SLO is a target or range for an SLI. An SLA is a broader agreement with users that typically says what happens if the service does not meet a commitment. Keeping the terms separate prevents contractual policy from being confused with the engineering target itself.

TermQuestion it answersExample
SLIWhat did users experience?fraction of valid requests that succeeded
SLOWhat experience are we targeting?99.9% success over a window
SLAWhat commitment/consequence exists?credit/contract response when target is missed
02 — indicators

Measure a service level, not whatever metric is convenient

The ideal SLI directly represents the behavior users care about. Sometimes a proxy is necessary: client latency is more representative than server latency, but client instrumentation may be unavailable. The gap between proxy and user experience should be understood rather than ignored.

Different systems require different measures. Serving systems emphasize request latency and success; data/storage systems may emphasize durability or freshness. An SLI should be carefully scoped to the relevant operation and population.

03 — aggregation

Raw measurements need the right summary

Service metrics are collected over windows and turned into rates, averages, or percentiles. Aggregation can hide important behavior. Averages are especially weak for latency distributions because a small slow tail may cause serious user pain while barely moving the mean.

Percentiles or threshold-style objectives expose the tail. It can be useful to define more than one latency threshold so the service describes both common performance and extreme-but-still-acceptable behavior.

04 — objectives

Choose targets that can drive engineering

The Shakespeare sample service illustrates turning vague language like “quickly” into an explicit latency objective. The actual number is a product/engineering choice, not a universal constant. Some metrics such as incoming QPS are imposed by users rather than controlled targets; you can capacity-plan for them, but calling them an SLO is not always meaningful.

Targets should not simply copy current performance. They should encode what users need and what the organization is prepared to support. Very strict targets can create large ongoing cost, while loose targets fail to protect users.

05 — expectations

Published and observed reliability shape dependencies

Consumers build systems around the reliability they observe. If a service claims one target but behaves far better forever, downstream teams may accidentally treat it as infallible and omit fallback behavior.

An internal target can be more stringent than the external expectation to provide reaction time before users experience a breach. The service owner should also revisit SLOs as workload and product expectations evolve.

Availability/error-budget conversion:
SLO = 99.9% → allowed bad fraction = 0.1% = 0.001.
For 8,000,000 valid requests, budget = 8,000 bad requests.
This turns an abstract percentage into an engineering quantity.
06 — action

An SLO matters because it changes what you do

If latency rises but remains comfortably inside the target, an immediate reliability project may not be the best use of time. If an incident rapidly consumes the error budget, the same metric becomes urgent. SLOs therefore connect monitoring to prioritization.

The chapter is foundational because later topics—alerting, error budgets, on-call policy, capacity, and release decisions—depend on having this definition first.

07 — worked objective

Turn an objective into a failure budget

Suppose an API has a monthly availability SLO of 99.9% and receives 50 million valid requests in the evaluation window. The allowed bad fraction is 0.1%, or 0.001.

The budget is therefore 50,000 failed requests. If a rollout causes 15,000 failures, it spends 30% of the monthly budget in one event. That makes the impact comparable with other outages even if their durations differ.

For a latency objective, the same event-counting approach works: define 'good' as requests below the threshold, count good and valid events, and measure whether the good fraction meets the objective.

99.9% SLO → 0.1% error budget. 50,000,000 valid requests × 0.001 = 50,000 allowed bad requests.
08 — objectives are decision tools

An SLO that never changes a decision is probably decoration

The operational value of an SLO is that it lets engineers distinguish a metric fluctuation from a reliability problem. If latency rises but the user-visible objective and error budget remain healthy, emergency work may not be justified. If the budget is being consumed quickly, the team has evidence to slow launches and prioritize reliability.

This also protects against arbitrary perfectionism. Engineering can stop improving a metric once further improvement no longer serves users enough to justify its cost, and can spend the saved effort on features or other failure modes.

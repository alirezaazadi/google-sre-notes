Google Site Reliability Engineering Book · Chapter 10

Practical Alerting from Time-Series Data

This chapter moves from monitoring principles to a concrete time-series architecture. Borgmon collects standardized white-box metrics, stores history, evaluates rules over time, produces charts and alerts from the same data, and aggregates hierarchically so large services can be monitored without paging on every component.

01 — why time series

Monitoring at scale needs common data, not one script per check

Early monitoring often consists of custom scripts that run a check and page. Borgmon instead makes time-series collection the central primitive. Applications expose metrics in a common format; monitoring stores history; rules derive rates, ratios, distributions, dashboards, and alerts.

That separation matters because the same data can answer a real-time alert and a retrospective debugging question. The monitoring system no longer has to spawn a special-purpose process and network request for every check.

02 — instrumentation

Expose machine-readable state

The chapter shows the old `/varz` style endpoint: one fetch can expose counters such as total HTTP requests and errors. Mapped variables add labels and histograms—for example, response counts by status code.

Instrumentation should make the service's meaningful internal state cheap to collect. A monitoring platform cannot recover semantics that the application never exported.

Example exposed counters:
HTTP 200 = 25, HTTP 500 = 12
observed explicit error fraction = 12 / (25 + 12) ≈ 32.4%.
A rule language can compute that ratio from counters instead of requiring a custom check script.
03 — hierarchy

Aggregate monitoring like the service topology

A Borgmon can scrape another Borgmon. Teams commonly operate cluster-level collectors and global collectors, and very large services can shard below the cluster. Each layer can aggregate/summarize and intentionally discard detail that is no longer useful at the next level.

The architecture keeps global monitoring feasible while preserving a path to drill into finer-grained data when debugging.

04 — rules

Turn data into derived signals

Rules perform arithmetic over time series to create higher-level metrics: request rates from counters, error fractions, availability, percentiles, and conditions that generate alerts. Because history is available, rules can compare time windows rather than inspecting one instantaneous value.

Simple, readable rules are a reliability feature. If the on-caller cannot understand why an alert fired, the monitoring system itself becomes part of the incident.

05 — scale

Do not page on individual component failure

At Google's scale, one machine failing is normal. The service architecture should absorb it, and monitoring should aggregate enough to detect user/service impact rather than wake humans for each expected component churn event.

At the same time, retain component-level data for diagnosis. The right monitoring system is high-level enough for alerting and granular enough for troubleshooting.

06 — maintenance

Monitoring is production software

Rules, dashboards, data retention, cardinality, and aggregation all create maintenance cost. The chapter's architecture aims to keep the system simple enough that engineers can adapt it as services evolve.

After incidents, update alert rules and instrumentation based on what was actually useful. Monitoring is not finished when the first dashboard exists.

07 — data model

Why standardized time series changed monitoring

Borgmon replaced fleets of one-off check scripts with a common way for programs to export metrics and a common engine that collected, stored, queried, charted, and alerted on those measurements. That separation matters: application code exposes state; monitoring rules decide how to aggregate and interpret it.

Targets expose simple machine-readable variables. A Borgmon periodically scrapes those targets, attaches labels such as job, service, instance, and zone, and stores timestamp/value pairs as time series. Because the same data feeds both charts and alerts, an engineer can inspect the history behind an alert instead of treating the check as a black box.

Monitoring instances can also aggregate other monitoring instances, mirroring the service topology: task-level data rolls into cluster summaries and then global summaries. This lets the alerting layer reason about service health instead of paging for every failed machine.

08 — capacity math

Monitoring infrastructure has capacity math too

The chapter gives a useful concrete estimate for Borgmon’s in-memory arena. A single time-series sample uses about 24 bytes. With one million distinct time series, sampled once per minute, keeping roughly 12 hours of data means about 720 samples per series.

That is 1,000,000 × 720 × 24 bytes ≈ 17.28 GB, which is why the chapter states that one million series for 12 hours at one-minute resolution fits in under roughly 17 GB of RAM after implementation details/rounding. Older data can be archived to a larger, cheaper time-series database.

This calculation illustrates an important monitoring principle: label cardinality and sampling frequency are resource decisions. Adding a high-cardinality label can multiply the number of series dramatically.

1,000,000 series × 720 samples/series × 24 B/sample ≈ 17.3 GB of raw sample memory.

Load Balancing at the Frontend

Frontend load balancing decides which datacenter should serve a user before local server selection occurs. The chapter compares global objectives such as latency versus throughput, examines DNS-based routing and its caching/control limits, and explains how traffic management must account for capacity and failure rather than simply geographical proximity.

01 — objective

There is no single 'optimal' route

A search request is latency-sensitive, so a nearby datacenter with low RTT is attractive. A large video upload may value throughput and first-attempt success more than minimum RTT, making a less congested path preferable.

Global load balancing therefore optimizes a service-specific objective under capacity and failure constraints. The nearest site is not always the best site; caches, network congestion, available capacity, and traffic class also matter.

02 — physics

A giant central server would still be wrong

Even an imaginary infinitely powerful machine would be constrained by network distance and would remain a single failure point. Large services need geographical distribution for both latency and resilience.

The speed of light creates real latency lower bounds. Global balancing is partly about placing computation/data close enough to users while retaining enough alternative capacity for failures.

03 — DNS

DNS is a natural but imperfect first balancer

DNS can return different A/AAAA records and can direct resolver populations toward datacenters. It is simple and occurs before the client connection begins.

The weakness is control. Clients/resolvers cache answers, honor TTLs inconsistently, and the authoritative server often sees the resolver rather than the actual user. Weighted behavior for HTTP is also limited. Consequently, traffic cannot be moved with perfect immediacy or per-request precision.

04 — capacity

Routing must be capacity-aware

A datacenter can be healthy but full. Sending more requests there because it has the best latency will raise queueing and eventually cause failures. Global systems need a model of available serving capacity and should divert new traffic before the local fleet saturates.

Failover planning is especially important: when one site disappears, the same global demand is redistributed to the survivors. Those sites need spare capacity or intentional load shedding.

Simple regional headroom example:
3 equal regions serve 30k QPS total → ~10k each normally.
If one region fails, remaining demand ≈ 15k QPS per surviving region.
A design provisioned for only 11k/region cannot survive the advertised one-region failure without shedding or degrading.
05 — layers

Global and local balancing solve different problems

Global balancing chooses a datacenter/site according to user distance, traffic type, capacity, and health. Once inside that site, datacenter load balancing selects one of many backend tasks and focuses on even resource utilization and avoiding bad tasks.

Keeping these layers conceptually separate helps troubleshooting: a user can be routed to the wrong site even if in-site balancing is perfect, or one local task can be hot even while global routing is correct.

06 — DNS and VIPs

Frontend balancing happens at multiple layers and timescales

DNS is useful for choosing a broad serving location, but DNS caching means the routing decision persists beyond the instant it was made. The authoritative server often sees the resolver rather than the end user, and a long TTL slows failover while a very short TTL increases lookup load and still cannot force every resolver to obey perfectly.

Inside a chosen site, a virtual IP can provide a stable destination while network load balancing distributes flows to a set of frontend tasks. This local mechanism can react faster than DNS to individual frontend churn.

The architecture therefore separates global routing—choose a healthy, appropriately located datacenter with enough capacity—from local routing—choose an actual frontend instance. Each layer needs health and capacity information appropriate to its scope.

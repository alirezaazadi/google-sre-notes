Testing for Reliability

Testing reduces uncertainty introduced by change. The chapter connects traditional software tests with production tests, load/stress testing, canaries, configuration tests, disaster testing, and MTTR: a failure caught before deployment effectively has zero production repair time.

01 — confidence

Past reliability does not automatically predict future reliability after change

If a service never changed, historical behavior might predict future behavior reasonably well. Real systems change code, machines, configuration, traffic, and dependencies. Each change introduces uncertainty.

Tests demonstrate areas of equivalence: if behavior is verified before and after a change, some uncertainty is removed. More relevant coverage lets the organization make more changes before predicted reliability falls below the acceptable level.

02 — zero MTTR

The best production incident is one blocked before production

A monitoring system finds a defect only after the bad code reaches users; the service then has a nonzero mean time to repair. If a system-level test reproduces the same failure in the release pipeline and blocks the push, the user-visible MTTR for that defect is effectively zero.

Better preproduction testing therefore increases user-experienced MTBF while lowering the number of incidents responders need to repair.

03 — traditional

Use a hierarchy of tests

Unit tests cheaply verify small components. Integration tests verify interactions. Larger system tests exercise realistic paths. The test pyramid idea is economic: keep many cheap deterministic tests near the bottom and fewer expensive broad tests at higher layers.

Coverage percentage alone is not sufficient; what matters is whether important semantics and failure paths are exercised. A high line-coverage number can still miss a distributed coordination failure.

04 — production tests

Some properties exist only in a live system

Production tests include monitoring validation, canary releases, configuration tests against real infrastructure, and controlled failure/disaster exercises. They answer questions that mocks cannot: does the failover actually work with today's permissions and topology? Does the service hold latency under real workload?

Production testing must be bounded by blast-radius controls. The purpose is to gain confidence, not to create uncontrolled outages.

05 — load/stress

Find the performance envelope

Load testing measures behavior at expected demand and identifies capacity at target latency. Stress testing intentionally goes beyond normal levels to find where the system degrades or fails and whether that failure is graceful.

A capacity number without a latency/error target is incomplete. “Handles 20k QPS” means little if p99 becomes 30 seconds at 15k.

Example capacity statement:
at 12,000 QPS: p99 = 220 ms, errors = 0.05%
at 15,000 QPS: p99 = 1.8 s, errors = 1.2%
If SLO is p99 < 500 ms and errors <0.1%, practical capacity is closer to 12,000 QPS, not the highest load before crash.
06 — failure testing

Test the recovery mechanisms you plan to rely on

Inject machine/dependency/site failures where safe, test rollback and restore, validate monitoring, and periodically exercise disaster plans. Backups that have never been restored and failover code that has never run are assumptions, not evidence.

Test results should update capacity models, runbooks, alerting, and architecture. A failing reliability test is useful because it reveals missing confidence before users pay the cost.

07 — zero MTTR

A test can convert a production repair into a blocked release

The chapter makes a useful connection between testing and MTTR. If a system-level test detects exactly the failure that production monitoring would have detected, the release can be blocked before users ever see it. From the user’s perspective, that defect had effectively zero MTTR because it never became a production outage.

This is why reliability testing should be designed from real failures. After an incident, ask whether the same condition can be expressed as a regression, integration, configuration, stress, or system test. Every production failure converted into a preproduction test raises the effective MTBF users experience.

08 — production tests

Production is not hermetic, so test deployed reality too

Staged rollouts mean production may temporarily contain several binary and configuration versions at once. A test that uses the newest configuration from source control against an older live binary can produce a result that is correct for neither real serving path.

Configuration tests therefore compare checked-in intent with what production is actually running. Stress tests find the resource boundary where graceful operation ends. Canarying exposes a small live population to a new version and observes the less predictable behavior that hermetic tests cannot reproduce.

These layers complement rather than replace unit/integration/system tests. The cheaper tests catch local defects quickly; the production-facing tests validate assumptions that only exist in the deployed environment.

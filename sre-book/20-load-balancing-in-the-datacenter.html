Load Balancing in the Datacenter

Within a datacenter, many interchangeable backend tasks must share a query stream evenly enough that one hot task does not cap the whole service. The chapter develops health/flow control, graceful removal, several request-selection policies, and subsetting to control connection/state costs at very large backend counts.

01 — ideal

The hottest task determines usable fleet capacity

Services may range from a few backend processes to more than 10,000, with a typical service often in the 100–1,000 task range. A client task chooses one backend for each query.

In the ideal distribution every backend consumes the same resources. If load is uneven, the most-loaded task reaches its capacity first, forcing global traffic to stop increasing even while other tasks are idle. The chapter formalizes wasted capacity as the sum of the gap between the hottest task's CPU and every other task.

Example: a service can reserve 1,000 CPUs but effectively use only ~700 if poor balancing creates persistent hot tasks.

02 — health

Do not route new work to tasks already drowning

A simple flow-control approach tracks outstanding requests from a client to each backend. When the count crosses a limit (the chapter mentions 100 as a reasonable value for many backends), that client temporarily treats the backend as unhealthy.

This protects against a server that is alive but so slow that work accumulates. Binary health checks alone cannot represent that kind of overload.

03 — lame duck

Remove tasks without breaking in-flight work

During rollout or shutdown, a backend can enter lame duck mode: stop accepting new work/appear unhealthy to selection while finishing existing requests. This is safer than terminating a process while clients still have active requests or connections.

Graceful drain is an important operational primitive for deployments and maintenance because it turns task removal into a controlled state transition.

04 — algorithms

Why naive round robin can waste capacity

Round robin assumes requests have similar cost and backends are equally loaded. Random selection has similar variance. Real queries vary in cost and tasks carry different residual work.

More adaptive policies use client-observed outstanding work, backend utilization, or a “power of two choices” style: choose a small random candidate set and send the request to the least-loaded candidate. Two choices can dramatically reduce imbalance without requiring global perfect state.

05 — subsetting

Every client connecting to every backend does not scale

If thousands of clients maintain connections and load state for thousands of backends, the connection graph becomes enormous. Subsetting gives each client a smaller, deterministic subset of backends.

Subsets must be designed so load is statistically balanced, failures do not strand clients, and backend churn does not cause massive connection reshuffling. Stable hashing/permutation strategies help.

Connection-scaling intuition:
2,000 clients × 5,000 backends = 10,000,000 client→backend relationships if fully connected.
If each client uses a subset of 100 backends, relationships fall to 200,000—50× fewer—while subsets can still overlap enough to spread load.
06 — deep stacks

Imbalance can amplify through dependencies

A frontend may load-balance to an application, which fans out to another service, which fans out again. A small imbalance at each layer can combine into large hotspots. Request cost and load signals therefore need to be meaningful across the call graph.

No load-balancing algorithm has perfectly current global state. Backends still need local overload protection, and clients need bounded retries when a chosen backend refuses work.

Appendix C — Results of Postmortem Analysis

The appendix demonstrates organizational learning at scale. A standardized postmortem taxonomy lets Google aggregate thousands of incidents and discover that some classes of change and software/process failure contribute far more outages than hardware failure.

01 — taxonomy

Turn stories into analyzable data

A single postmortem is a narrative about one incident. If postmortems consistently record trigger and contributing/root-cause categories, the organization can analyze the whole incident population instead of relying on memorable anecdotes.

The distinction matters: the trigger is the event that initiated the outage (for example, a binary push), while deeper categories describe why the system was vulnerable (software defect, development process, complex behavior, deployment planning, and so on).

02 — triggers

What triggered outages in the analyzed sample

The standout result is that controlled software/configuration change dominates the trigger distribution. Binary and configuration pushes together account for 68% of the listed triggers. Hardware is only a small fraction in this sample.

That does not mean hardware reliability is unimportant. It means the organization’s next reliability investment should be informed by observed incident frequency/impact rather than an intuition that physical failure must be the primary cause of outages.

03 — causes

Contributing root-cause categories

These categories suggest broader controls than fixing one bug: stronger testing and code review, canary/deployment systems, configuration validation, simpler interfaces, and safer change planning can prevent whole classes of incidents.

04 — decisions

Use the dataset to fund systemic work

Rank patterns by impact as well as count. A frequent tiny event and a rare catastrophic data-loss event should not necessarily receive the same priority.

After deploying systemic controls, continue collecting the same taxonomy and check whether incident frequency, severity, or error-budget consumption actually declines. Without that feedback, the postmortem program can become a document archive instead of a reliability system.

Simple observation from the published trigger table:
binary pushes 37% + configuration pushes 31% = 68%.
That is strong evidence for investing in safer change mechanisms such as canaries, validation, progressive rollout, and rollback.

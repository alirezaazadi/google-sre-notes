Google SRE Workbook · Chapter 13

Data Processing Pipelines

A production pipeline is not just a sequence of jobs. It is a service with customers, SLOs, release procedures, dependency failure, persistent data, cost, correctness requirements, and recovery obligations. This chapter shows how to design and operate pipelines with the same discipline used for online services.

01 — applications

Start from what the pipeline is for

The chapter deliberately begins with applications rather than technologies. Pipelines may perform ETL/data transformation, analytics, machine learning, indexing, billing, or other business-critical processing. A high-level pipeline definition can hide many stages, and the output of one stage becomes the input of another; the reliability question is therefore about the end-to-end product, not whether one worker is alive.

The fictional game Shave the Yak illustrates analytics: mobile/web events flow into BigQuery, upstream data is refreshed three times per day, and a downstream aggregate is used for business reporting. Dressy illustrates machine learning: product images and user information are preprocessed, models are trained and evaluated, model artifacts are published, and an online service uses them for recommendations.

02 — dressy

Reliability of an ML pipeline is end-to-end

Dressy wants newly uploaded products to influence recommendations within 12 hours. It creates streaming preprocessing steps for image classification and customer profiles, trains TensorFlow models, stores the model artifact in Cloud Storage, evaluates it against test data, and finally serves predictions to web/mobile clients.

When recommendations become stale or intermittent, the diagnosis is not simply “is the model server up?” The chapter asks whether data is stuck before preprocessing, whether a bug/spam/bad feature selection produced a poor model, and whether a newly generated model was actually published or an old model is still serving. That is a pipeline-specific version of SRE’s usual rule: monitor the user outcome, then use stage metrics to find the cause.

03 — slos

Define pipeline SLOs around data behavior

The chapter proposes several forms of freshness SLO: X% of data is processed within Y time; the oldest data is no older than Y; or the job completes successfully within Y. Shave the Yak could require 99% of score-affecting user actions to appear on the scoreboard within 30 minutes.

Correctness is harder because many data products do not have a naturally known answer. The recommendation is to manufacture a known answer where possible: test accounts or generated “golden data” can pass through the real production pipeline, and expected output can be compared with observed output. A backward-looking correctness target can also be appropriate—for example, no more than a small fraction of invoices being wrong over a quarter.

Coverage/completeness may be a separate SLI. A daily aggregate that arrives on time but contains only 70% of the expected records is not fresh and correct enough simply because the job exited successfully.

Example freshness SLO:
99% of score updates must appear within 30 minutes.
If 2,000,000 score-affecting events occur in the SLO window,
allowed late events = 1% × 2,000,000 = 20,000.
The error budget belongs to the customer-visible data outcome, not one pipeline task.
04 — development

A pipeline needs a release lifecycle

Begin with a prototype, then execute against real or representative data. The chapter suggests experiments such as a 1% dry run in a nonproduction environment, gradually scaling while measuring resource use and performance.

Staging matters especially for pipelines because unit tests cannot reproduce every interaction between persistent data and multiple stages. Use representative production data and compare new output against a known-good previous output.

Canarying a pipeline differs from canarying a stateless server. You may need to process the same production data while suppressing production writes, use two-phase/idempotent mutations, or canary a fraction of data rather than a fraction of tasks. Verification may require waiting for a complete processing cycle.

For a major change, the chapter suggests a staged data ramp such as roughly 1% → 10% → 50% → 100%. The key protection is to prevent corrupted experimental output from being promoted into low-latency serving paths.

05 — resource behavior

Hotspots, autoscaling, and stage-level efficiency

Pipelines can be globally underutilized while one tablet, row lock, disk, hot key, worker, or oversized work unit becomes the bottleneck. A good framework can rebalance work into smaller chunks; applications should also be able to isolate or skip a pathological record/user rather than stall all progress.

Autoscaling is attractive because variable streaming/batch workloads do not justify permanent peak capacity, but resource planning still needs growth forecasts, storage/network replication costs, and dependency limits. The chapter recommends evaluating efficiency at each stage even though the reliability objective is end-to-end.

Access control, privacy, and data integrity belong in the pipeline design because data is commonly persisted at intermediate stages; production convenience should not widen access unnecessarily.

06 — failure

Prefer stale data to silently wrong data

The chapter identifies data delay and data corruption as common failure classes. For delay, respect data dependencies rather than letting a downstream stage process incomplete input. Stale output is often safer than newly generated incorrect output.

For corruption, first stop additional bad data from entering or being served. Then restore a known-good version or reprocess the affected window. Selective reprocessing can reduce recovery cost; persisted intermediate checkpoints can avoid rerunning the entire pipeline.

Operational tooling should expose the execution graph, age/backlog at stages, failed or slow work units, logs for the relevant work, limiting resources, and enough history to compare current behavior with previous runs. The goal is to reduce both MTTD and MTTR.

Recovery rule: contain the bad data path first; only then repair or replay. Data correctness failures can propagate far beyond the original stage.

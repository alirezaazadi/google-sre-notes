Configuration Specifics

Once configuration becomes large or repeated across services, treat it like software: choose structures that represent the domain clearly, eliminate duplication with abstraction, generate consumer-specific formats, validate and test outputs, and decide deliberately whether evaluation happens at build time or runtime.

01 — why

Copy/paste configuration becomes toil and risk

Large estates accumulate similar YAML/JSON/XML files with small local differences. Copying an existing file is easy at first, but repeated values drift, fixes must be applied many times, and teams cannot tell whether differences are intentional.

The chapter therefore considers configuration languages such as Jsonnet: the point is not that one language is mandatory, but that functions, imports, variables, assertions, and composition can represent repeated intent more safely than thousands of nearly identical raw documents.

02 — representation

Use data structures that match the thing you are configuring

Objects/maps are useful when elements have stable names and callers frequently override by name. Arrays are natural when ordering matters and items are primarily a sequence. Picking a representation simply because the output format supports it can make composition awkward.

Group settings along functional boundaries. Configuration structure should help a reader understand which options control one concept and which are independent. A giant flat namespace makes interactions harder to see; an arbitrarily deep hierarchy can be just as confusing.

Object/mapNamed entities and keyed overridesOrder is less natural
Array/listOrdered sequences or repeated anonymous itemsTargeted override/merge can be awkward
Function/abstractionRepeated patterns with meaningful parametersOver-abstraction can hide generated behavior
Template stringLast resort for nonstructured outputWeak semantic validation; quoting/escaping hazards
03 — generation

One source can drive multiple systems

A structured configuration layer can generate the formats expected by several consumers. For example, define a port or service endpoint once, then generate both application/server configuration and an infrastructure/firewall declaration from that same value.

This removes cross-system drift: you no longer depend on an operator remembering to edit multiple repositories with matching numbers. It also enables assertions about relationships before any generated artifact reaches production.

When the target format cannot be represented structurally, string templating may be necessary, but the chapter treats it as less desirable because the tooling cannot reason as well about semantics.

04 — testing

Test configuration at several layers

Configuration deserves parsing/type/schema checks, semantic assertions, unit or golden-file tests of generated fragments, and integration tests against consumers. A generated file that is syntactically valid can still ask a service to allocate impossible resources or refer to a nonexistent dependency.

Testing should be close enough to production to reveal consumer behavior while still cheap enough to run before rollout. Reuse production configuration where appropriate, but do not make nonproduction testing inseparable from production side effects.

05 — evaluation

Build-time versus runtime evaluation is a trade-off

Evaluating configuration at build/deploy time makes failures visible before a serving process accepts the new state and can produce a concrete artifact for review. Runtime evaluation enables dynamic behavior and may reduce deployment coupling, but it moves parser/interpreter complexity and failure into the serving environment.

Decide based on change frequency, rollback needs, dependency on runtime information, and blast radius. Whichever model you use, a production rollout still needs progressive deployment and observability.

Key mindset: “configuration” is not an exemption from software-engineering discipline; it is code/data that can change production semantics.
06 — compatibility

Design for mixed versions

During rollout, different machines may briefly run old/new binaries and old/new configuration. Define which combinations are supported. If every config update requires an instantaneous fleet-wide switch, the system has created an unnecessarily fragile deployment dependency.

Rollback must be possible without reconstructing yesterday’s values by hand. Version the source and generated artifacts, record what is currently serving, and preserve enough history to return to a known-good state.

07 — Jsonnet's purpose

Use programmable configuration to remove repetition, not to hide behavior

The chapter uses Jsonnet because large structured configurations often repeat nearly identical objects. Variables, functions, imports, object composition, and assertions let operators express the shared intent once and generate the concrete JSON/YAML consumed by downstream systems.

The value is strongest when configuration has real structure: a service definition reused across environments, or one logical setting that must generate related config for multiple systems. The abstraction should make the final output easier to inspect, not create another opaque programming layer.

Generated configuration remains data at the consumer boundary. That means the application does not need a full programming-language runtime in its critical serving path; the expressive layer can be evaluated earlier and its output validated and versioned.

08 — deployment semantics

Configuration is distributed state

Once configuration controls many processes, the application mechanism matters as much as the syntax. Ask whether every target switches atomically, whether rollout is gradual, and how the system behaves while some tasks have old config and some have new config.

Compatibility must include binary/config combinations. A new config may mention a feature that old binaries do not understand, while a rollback to an old config may be incompatible with state produced by a new binary.

Treat the generated output as a release artifact: validate it, diff it, test it, canary it, observe the effects, and keep a known-good version for rollback.

Appendix A — Example SLO Document

The appendix turns SLO theory into an implementable document for the fictional Example Game Service. Its real lesson is precision: another engineer should be able to reproduce the SLI calculation from the document without asking what “available” or “fast” means.

01 — structure

What an SLO document contains

The Example Game Service description gives enough architecture/context to understand what users do: a REST API supports gameplay, game state is stored, score processing produces league data, and an HTTP serving path exposes results.

The example uses a four-week rolling evaluation window. The document also records authorship, reviewers/approvers, approval date, and a revisit date. These fields make the SLO a maintained engineering agreement rather than an anonymous number in a dashboard.

02 — availability

Define numerator and denominator

For the example API, availability is based on load-balancer request metrics: requests that do not return server-side 5xx responses count as successful relative to the valid request population. The key is not the particular percentage; it is that the measurement source and classification are explicit.

Client errors such as many 4xx responses may be excluded from a service-availability numerator because the service cannot necessarily make an invalid request succeed. That classification must still be deliberate: if an internal bug produces incorrect 4xx responses, blindly excluding them would hide user impact.

03 — latency

Describe the distribution, not one average

The example uses multiple latency thresholds rather than a single mean. That expresses both the common experience and the slow tail. Another engineer can translate those thresholds into counters/histograms and evaluate compliance over the same window.

The exact targets vary between service paths because the API and HTTP-facing service have different behavior. A single product can therefore have several SLOs as long as each corresponds to a meaningful user outcome.

Example SLO-document calculation pattern:
availability SLI = good requests / valid requests.
If 970,000 of 1,000,000 valid requests meet the success rule,
measured availability = 97%.
The document must make “good” and “valid” unambiguous.
04 — use

Treat the appendix as a template, not a target

When adapting the structure, list user-facing paths, define the event population and good-event condition, identify the authoritative instrumentation, state the window and target, explain why the target is appropriate, and name who reviews changes.

The document should change when evidence changes—new user journeys, monitoring improvements, product expectations, or a realization that the current SLI does not correlate with customer pain.

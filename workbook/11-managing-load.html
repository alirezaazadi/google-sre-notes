Managing Load

No single mechanism makes a service safe under changing demand. The chapter builds a traffic-management system from load balancing, autoscaling, load shedding, health checks, quotas, and conservative capacity planning—and then shows why those mechanisms must understand one another.

01 — request path

How Google Cloud Load Balancing moves a request

The chapter first makes load management concrete by walking a request through Google Cloud Load Balancing. Rather than relying on DNS geolocation for per-site routing, Google uses anycast: the same virtual IP can be announced from many locations, and BGP normally brings the packet to a topologically nearby frontend site. This removes one major source of stale client-side routing decisions.

Anycast alone is not enough. A changing BGP route can send later packets of an existing TCP flow to a different site, where there is no connection state. Google’s “stabilized anycast” uses Maglev to forward packets toward the appropriate frontend site and preserve the flow. Maglev itself is a distributed packet-level load balancer running on commodity machines; ECMP spreads packets across Maglev instances, while connection tracking and consistent hashing keep a flow pointed at a backend without requiring every Maglev to share per-connection state.

Above that packet layer, the Google Front End (GFE) terminates TCP/TLS, understands HTTP, chooses the backend service, health-checks backends, and maintains persistent connections to recently active backends. GSLB supplies global service-level decisions, including steering away from unhealthy clusters.

02 — case study

Pokémon GO: demand was not what monitoring said

Niantic load-tested Pokémon GO to 5× its most optimistic traffic estimate, but launch traffic reached nearly 50× that original estimate. That alone would stress almost any system, but the more interesting failure came during migration to GCLB: the true client demand turned out to be about 200% higher than the traffic previously observed by the frontend proxies.

Why? The proxies were so overloaded that they could not accept all inbound connections. Requests rejected before the application stack saw them never appeared in the normal request metrics. The lesson is subtle and important: throughput observed by a saturated server is not the same thing as demand. When capacity drops, server-side observed traffic can fall exactly when client demand is highest.

Slow, overloaded backends then triggered load-balancer retries. The client application also retried. When shared components restarted and produced bursts of fast failures, those clients became synchronized and created a classic thundering herd; the chapter reports spikes as high as 20× the previous global RPS peak.

Planning example from the case:
load test capacity ≈ 5 × optimistic estimate
actual launch ≈ 50 × optimistic estimate
→ actual demand ≈ 10 × the tested capacity target.

This is why capacity planning must include uncertainty and why demand should be measured as close to the client as practical.
Failure chain: hidden demand → slow backends → load-balancer retries → client retries → synchronized spikes → even less usable capacity.

03 — recovery

Containment before perfect scaling

Traffic SREs first isolated the GFE population serving Pokémon GO from the general pool, limiting collateral damage to other GCLB users. They enlarged that isolated pool, which moved the bottleneck back into Niantic’s stack, and then—with Niantic’s agreement—applied administrative rate limits so client demand could not continuously overwhelm recovery.

Afterward, Niantic added jitter and truncated exponential backoff. Google added qualification/load testing specifically for slow or misbehaving GFE backends. Both organizations learned to estimate load closer to the source rather than treating accepted backend requests as true demand.

General pattern: when a system is collapsing, reducing accepted work can restore more useful throughput than blindly adding retries or capacity.
04 — autoscaling

Autoscaling is delayed feedback, not infinite capacity

Autoscaling is useful when reserved capacity is temporarily insufficient, but the autoscaler itself only sees signals after load has already changed. New instances also need time to start, load software, warm caches, register with health checks, and receive traffic. A user-facing service therefore needs headroom; you cannot run permanently at the bottleneck and expect autoscaling to rescue every spike.

Unhealthy instances can distort average utilization. If an autoscaler includes nonserving instances in the average, it may conclude that the fleet is underutilized and fail to add capacity. Better approaches include basing scaling on capacity seen by the load balancer, ignoring new instances until they are ready, and combining autoscaling with autohealing.

Stateful systems add another complication: adding instances does not help if session affinity keeps hot users on their original backends. Task-level balancing or consistent hashing may be needed first. Vertical autoscaling can help with hotspots, but may overprovision the quiet instances too.

  • Scale up aggressively enough to avoid overload; scale down more conservatively because premature scale-down can immediately re-create overload.
  • Set minimum and maximum bounds. A CPU-consuming bug can otherwise cause the autoscaler to exhaust all available quota.
  • Provide a kill switch/manual override that on-callers know how to use.
  • Analyze downstream dependencies. Scaling the frontend can amplify load on a database that cannot scale at the same rate.
  • Consider shared quota: one rapidly growing microservice can consume the quota needed by the rest of the application.
05 — interactions

When Load Shedding Attacks

The fictional Dressy service demonstrates that individually sensible control systems can interact catastrophically. Three regions initially serve about 90 RPS each. As traffic rises, region A reaches its shedding threshold first. Its servers begin rejecting work to cap CPU. Because rejected requests are cheap, measured CPU cost per request drops.

The load balancer is utilization-aware but does not know which requests are successes and which are intentionally shed. It therefore concludes that region A is unusually efficient and sends more traffic there. Region A eventually receives about 400 RPS while B and C fall to roughly 40 RPS, and most requests in A return 503s.

The root problem is not that load balancing or load shedding is intrinsically wrong. The problem is that their signals have incompatible meanings. The chapter suggests making rejected requests look extremely expensive to the balancing logic (for example, accounting them as >100% utilization) so the balancer steers away from a shedding region.

Design lesson: load balancing, autoscaling, and load shedding are one control system even if different teams built them.

These are not trivia questions. A strong answer explains the mechanism, the reason for it, and the trade-off.

Question 2

Question 3

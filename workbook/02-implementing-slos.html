01 — why

Why SREs need SLOs

Engineering time is scarce. Without explicit reliability targets, teams easily spend too much time polishing reliability that users do not need—or too little time fixing reliability that users do need. SLOs create a common data-based way to compare that opportunity cost against feature work.

The chapter goes further than treating SLOs as reporting. SLOs drive SRE work: short-term defense of the objective, medium-term projects that keep the objective achievable, and decisions about whether a service needs more or less SRE attention.

A useful SLO therefore needs teeth. A dashboard that says '99.9%' but changes no engineering decision is not yet functioning as an SRE mechanism.

Key mindset: the purpose of an SLO is not to make a graph green. It is to improve decisions.
02 — sli

Start with the user and define SLI specifications

Choose one application first, identify who its users are, and list the critical ways they interact with it. Then draw a high-level architecture showing request flow, data flow, and critical dependencies. This prevents the monitoring system from dictating what you think matters.

The chapter strongly favors SLIs that can be expressed as a ratio of good events / valid events. Examples include successful HTTP requests divided by all valid HTTP requests, calls that complete under a latency threshold divided by all calls, or requests served with sufficiently fresh data divided by all such requests.

This normalized 0–100% form is convenient because the SLO is a target percentage and the error budget naturally becomes 100% minus that target.

The chapter distinguishes SLI specification from SLI implementation. The specification is the user outcome you care about independent of instrumentation. The implementation is the exact measurement method.

Source example:
99.9% SLO over 3,000,000 requests → error budget = 0.1% × 3,000,000 = 3,000 bad requests.
If one outage causes 1,500 errors, it consumes 50% of the budget.

03 — sources

Choose the measurement point deliberately

For request/response services, the chapter considers application logs, load-balancer monitoring, black-box monitoring, and client-side instrumentation. The closer the signal is to the user, the better its quality can be—but cost and coverage vary.

In the Example Game Service, load-balancer metrics are selected for API and HTTP availability/latency because they already exist and are closer to the user than backend logs. Any HTTP 5xx is counted as failure; other status classes are treated as successful for that particular availability definition.

For a data pipeline, different outcomes need different SLIs. Freshness can use a watermark; coverage compares expected versus processed records; correctness can use known-good test data or an independent expensive computation sampled against production output.

The important lesson is that correctness is not automatically observable. Sometimes you must create 'golden data' or an independent verification path specifically so correctness can be measured.

Precision vs recall: an SLI can miss real user pain (poor recall) or count technically bad events that users never notice (poor precision). Both are reasons to refine it.
04 — targets

Set an initial SLO and an evaluation window

The book previously warned against simply making current performance the SLO, because accidental overperformance can become an expensive permanent obligation. The Workbook softens that advice pragmatically: if you have no better evidence, current performance can be a starting point, provided you deliberately iterate.

Select a reporting/evaluation window that matches how you make decisions. The running example uses a four-week rolling window. Windows that are too short create noise; windows that are too long react slowly and can hide recent behavior.

Examine historical performance if available. Ask whether days that would have violated the proposed SLO correspond to incidents users actually noticed. If they do not, the SLI or target may be measuring the wrong thing.

If there is no historical data, configure a low-fidelity measurement now rather than waiting for a perfect telemetry stack. The chapter explicitly prioritizes establishing a feedback loop.

05 — agreement

Get stakeholder agreement and create an error-budget policy

Three groups must accept the SLO. Product management must believe it is sufficient for users. Development must agree to reduce risk when the budget is exhausted. The production/SRE team must believe the objective is defensible without heroic toil or burnout.

The error-budget policy is where the SLO becomes operational. Typical actions include prioritizing reliability bugs, temporarily dedicating engineering effort to reliability, or freezing selected production changes until sufficient budget returns.

The policy should be written before the argument happens. Otherwise, when reliability is poor, stakeholders will debate both the facts and the response while under pressure.

The document should record authors, reviewers, approvers, approval/revisit dates, service context, exact SLI implementations, SLO targets, and how the error budget is calculated and consumed.

Failure mode: an SLO approved by SRE alone is not a shared contract. If product and development do not accept the consequences of exhausting the budget, the mechanism will collapse exactly when you need it.
06 — iteration

Build a continuous-improvement loop

A mature SLO is not static. Compare SLO performance with customer complaints, manually discovered outages, support tickets, user research, and business metrics. The purpose is to test whether the SLI remains a useful approximation of user happiness.

If the SLO is green but users are unhappy, tighten or redesign the measurement. If the SLO is red but users remain happy, you may be spending engineering effort on reliability users do not value.

Review the cheapest/highest-return improvement first. Early iterations should favor quick learning over elaborate instrumentation because each iteration reduces uncertainty about what is actually worth measuring.

07 — decisions

Use error-budget cost to prioritize reliability work

The chapter gives a useful comparison. One bad API release causes 14,066 errors against an error budget of 109,897—about 13% of the budget. A rare database server failure causes 72,000 errors—about 65%. But if bad releases happen two or three times per year and the database failure happens only once every five years, annual expected error-budget cost can still make release safety the higher-value investment.

This is classic SRE thinking: do not prioritize solely by how dramatic one incident looked. Combine frequency × impact and make the decision using the reliability currency you already defined.

The chapter also presents a matrix using three dimensions—SLO performance, operational toil, and customer satisfaction. For example, meeting the SLO with low toil but low customer satisfaction suggests the SLO is too loose; missing the SLO with low toil but high customer satisfaction suggests it may be too strict.

At the advanced end, teams model critical user journeys rather than isolated RPCs, reason about dependencies, and may carefully experiment with relaxing reliability when they have budget to determine how technical metrics relate to business outcomes.

Source comparison:
Bad release: 14,066 / 109,897 ≈ 13% of budget.
Single database failure: 72,000 / 109,897 ≈ 65%.
But expected annual cost depends on frequency; recurring bad releases can justify fixing release safety first.

Questions you should be able to explain aloud

These are not trivia questions. A strong answer explains the mechanism, the reason for it, and the trade-off.

Question 1

Design availability and latency SLIs for a public API and tell me where you would measure them.

Question 2

Why can using current performance as the initial SLO be acceptable, and what is the danger?

Question 3

How would you resolve disagreement between product, developers, and SRE about an SLO?

Question 4

How can error-budget consumption help prioritize two very different reliability projects?

Introducing Non-Abstract Large System Design

A detailed, plain-English walk-through of Non-Abstract Large System Design — how Google's SREs turn a vague requirement into a real, resource-costed system, one honest failure at a time.

📖 Based on Chapter 12 of Google's SRE Workbook — sre.google/workbook/non-abstract-design. Ideas summarized in my own words; diagrams are original sketches, not the book's figures (the source is CC BY-NC-ND, so I can't reproduce or remix its text/images — go to the link for the official ones).
01 — the idea

What is NALSD, really?

It's a way of designing systems where you're never allowed to hand-wave. Every time you say "we'll store the logs" or "a server will handle it," you have to immediately ask: how many servers, how much disk, how much bandwidth — actually?

The name says it directly: Non-Abstract. No system runs on an "abstract cloud" — it runs on real disks with real IOPS limits, real network cards with real bandwidth caps, and real datacenters that occasionally lose power. NALSD forces you to keep translating your whiteboard boxes into numbers, over and over, until the design either survives contact with reality or breaks in a way you can now see and fix.

Key mindset: the exact numbers you land on matter less than the habit of producing them. A reasonable, honestly-derived estimate beats a precise-looking guess.

The four questions you keep asking

Every iteration of a design gets pushed through the same checklist:

1. Is it possible?

Forget cost for a second — is there even a design, in principle, that solves the problem?

2. Can we do better?

Is there a simpler or asymptotically faster way to do the same thing?

3. Is it feasible?

Given real machines, money, and time — can we actually build this at the required scale?

4. Is it resilient?

What happens when a disk, a machine, or an entire datacenter dies?

You don't march through these once — you loop through them, iteration after iteration, each time replacing whatever part of the design just failed.

02 — the problem

The example: a live ad click-through-rate dashboard

The book uses one running example throughout, so this summary sticks with it too. Google's AdWords needs to show every advertiser a dashboard of their click-through rate (CTR) — clicks ÷ impressions — for each ad and search term.

Two logs feed this: a query log (every search, with which ads were shown) and a click log (every click, with which ad and which search it belonged to). The dashboard has to join these two logs together by a shared query_id.

Targets to hit:
• 99.9% of dashboard loads finish in < 1 second
• 99.9% of the data shown is < 5 minutes old
• Scale: ~500,000 searches/sec and ~10,000 clicks/sec

Those SLOs are the whole game. Almost every design below dies because it can't hit the "fresh within 5 minutes" target, not because it can't store the data.

03 — attempt 1

Just... use one machine?

The cheapest possible design: dump both logs into a single SQL database on one box, index by query_id and search_term, and let a query join them on demand.

It's a useful starting point precisely because it's easy to reason about — and easy to break.

Why it collapses

Two independent failures:

  • Disk throughput: at 2 KB per log line and 500,000 queries/sec, that's roughly 86 TB of query logs a day — call it 100 TB once you round for overhead. A single machine can't sustain the write rate: even fast HDDs top out around 200 IOPS, meaning you'd theoretically need thousands of disks just for writes.
  • RAM: if you instead tried to keep it all in memory on a standard 64 GB box, you'd need on the order of 1,500+ machines' worth of RAM just to hold one day of data. That's not "one machine" anymore.
  • Reliability: even setting the math aside — one machine is one power cycle away from taking the whole dashboard down.
Verdict: not feasible, not resilient. But the exercise wasn't wasted — it told us exactly which numbers (IOPS, RAM) are the real constraints going forward.
04 — attempt 2

Batch it with MapReduce?

Obvious next move: don't fight one machine, spread the join across many with a MapReduce batch job. Feed it a chunk of query logs and click logs, get back CTR numbers per ad.

This solves the scale problem cleanly — throw more workers at it and it keeps working, no matter how huge the input.

Why it still fails: the freshness SLO. MapReduce processes logs in discrete batches. To hit "fresh within 5 minutes" you'd need tiny, frequent batches — but a click can land in a different batch than the query it belongs to, and once a batch closes, that click never gets joined. Batching and "always-fresh joins" are fundamentally in tension here.

→ so instead of chasing MapReduce workarounds, the design pivots to something built for continuous streams.

05 — attempt 3

LogJoiner: stop batching, start looking things up

Clicks are much rarer than searches (10,000/sec vs 500,000/sec), so scale the design around that asymmetry. Instead of joining two huge streams, build one big lookup table for queries, and only chase down the query for each click as it happens.

Three new pieces:

  • QueryStore — every query log entry, keyed by query_id, ready to be looked up on demand.
  • LogJoiner — for each incoming click, looks up its query in QueryStore and joins them. If the query hasn't arrived yet, it waits a bit and retries, then gives up after a timeout.
  • ClickMap and QueryMap — the joined results and the raw query counts, both organized by ad_id so the dashboard can fetch them instantly.

QueryMap ≈ 2 TB/day · ClickMap ≈ 20 GB/day · LogJoiner network load ≈ 400 Mbps
(small enough to run — except the 2 TB QueryMap still needs more small, fast writes than one machine's disks can sustain.)
Still not done: QueryMap's write pattern hits the same IOPS wall the one-machine design hit. Time to split the work across machines.
06 — attempt 4

Sharding: many small LogJoiners instead of one big one

Split the incoming logs across N LogJoiner instances using a simple rule: hash the query_id, take it modulo N, and route the record to that shard. Every shard now only sees a slice of the traffic, so each one stays comfortably within a single machine's IOPS and RAM budget.

QueryMap shards by ad_id instead (since that's the key the dashboard looks up by), and ClickMap reuses the same scheme.

The reliability catch

Sharding alone creates more single points of failure, not fewer — now you have N of them. The fix: send every record to two shards instead of one, spread across different machines. If one replica dies mid-join, its twin already has the work. Losing both replicas at once is rare enough that the SLO's error budget can absorb it — worst case, a brief window of slightly-stale data while the logs get reprocessed.

sketch — sharding + replica pairs for fault tolerance (original diagram)
One gap remains: all of this still lives in a single datacenter. Lose the datacenter, lose every ClickMap and QueryMap shard — and every advertiser's dashboard — at once.
07 — attempt 5

Multidatacenter: surviving a whole datacenter going dark

To survive a datacenter-scale outage, the data itself — not just the compute — needs copies in multiple, geographically separate datacenters. That's the textbook consensus problem: how do several replicas, in different places, agree on the current state without one becoming an unreliable single source of truth?

The recipe here: keep 3–5 replicas of ClickMap/QueryMap, and use a consensus protocol like Paxos so a write is only accepted once enough replicas agree they've seen it — surviving the loss of a minority of them, including an entire datacenter.

The cost of agreement: consensus needs at least one network round trip between distant datacenters — roughly 25 ms. That caps you at about 40 sequential operations/sec per process, so you compensate the only way you can: run many parallel processes, sharded by ad_id, so the 40/sec limit applies to thousands of shards at once instead of one global queue.

~1,000,000 queries/sec ÷ 40 ops/sec ≈ 25,500 parallel tasks needed
→ roughly 157 MB RAM and ~640 Kbps network per task
→ about 4 TB total RAM per datacenter ≈ only ~64 machines, using ~25% of network capacity

That's a genuinely comfortable margin — proof the design isn't just theoretically resilient, it's cheap enough to actually run.

sketch — replicas across datacenters agreeing via Paxos before a write "counts" (original diagram)
Checked against the original requirements: handles 10,000 clicks/sec and 500,000 queries/sec, dashboard reads stay fast because ClickMap/QueryMap are pre-joined and keyed by ad_id, and every stage scales horizontally — so if latency creeps up, you add machines rather than redesign.

takeaways

Using this yourself

  • Start absurdly simple (one machine), and let the numbers — not intuition — tell you where it breaks.
  • Convert every design into concrete units: bytes/day, IOPS, Mbps, machines. If you can't, you don't understand the design yet.
  • Freshness/latency SLOs often kill a design before capacity does — check them early.
  • Resilience isn't a bolt-on at the end: ask "what if this dies?" at every single iteration, not just the last one.
  • Perfect assumptions aren't the goal. Reasonable, explicit, checkable ones are.

Monitoring

Monitoring is an engineering system for alerting, diagnosis, visualization, planning, and experimentation. The chapter focuses on choosing the right data and architecture—not collecting everything—and on making service-level signals the entry point into deeper diagnostic telemetry.

01 — purposes

Monitoring has several different jobs

The chapter lists multiple monitoring use cases: alert on conditions that require attention, investigate and diagnose incidents, visualize service state, understand long-term trends, and compare behavior before/after a change or between experimental groups.

These use cases impose different requirements. Alerting needs low latency and high reliability; forensic analysis benefits from detailed logs; long-term planning may tolerate slower aggregation but needs retention. One monitoring backend may not optimize every use case equally well.

Start by naming the question you need the monitoring system to answer. A monitoring architecture chosen because it is fashionable often becomes expensive and still fails to answer the operational question.

Core principle: collect telemetry with purpose. Observability is not the number of metrics you have; it is your ability to answer important questions.
02 — metrics-logs

Metrics and logs solve different parts of the problem

Metrics are compact, structured, and efficient for aggregation. They make it easy to see the scale of a problem: how many errors, how much traffic, which status codes, which percentile, which region.

Logs preserve high-cardinality details that would be expensive or impossible to attach to every metric. They are strong for request-level context and root-cause investigation.

The chapter recommends keeping alerting primarily metric-based even when a single special event matters. If a log condition should alert, increment a metric counter for the event and alert on the metric. That keeps alert logic centralized.

One example moves HTTP status-code information from logs into metrics. Previously, an operator had to find a time range in a global error graph, search logs for failures, then guess whether one log entry represented a broad problem. Adding the status code as an appropriate metric dimension gave both scale and diagnosis context.

03 — architecture

Think about the monitoring system itself as a distributed system

Monitoring systems need reliability, scalability, query performance, retention, and migration strategies. The chapter discusses Google’s evolution from Borgmon to Monarch and the use of Viceroy dashboards as a compatibility layer during migration.

A useful architectural lesson is decoupling visualization from the metric storage system. If dashboards can query both old and new backends, teams can migrate gradually instead of rewriting every console at once.

Monitoring infrastructure should not become an opaque dependency whose failure blinds the operators. Understand its availability and failure behavior, especially for paging paths.

Migration lesson: compatibility layers can reduce the risk of replacing foundational operational infrastructure.
04 — purpose

Put SLI metrics first, then diagnostic metrics

When an SLO alert fires, the first dashboard should show the SLI and user impact prominently. That tells responders whether the service is violating an objective, but it usually does not explain why.

The chapter recommends diagnostic monitoring for intended changes, dependencies, served traffic, and resource saturation. If you cannot quickly correlate a regression with a release/config change, you lose valuable incident time.

Dependency metrics should include volume, latency, and response/error behavior. Saturation monitoring should cover whatever bounded resources can limit work: CPU, memory, disk, queues, thread pools, file descriptors, quotas, and garbage-collection behavior.

High-cardinality information such as arbitrary user IDs generally belongs in logs rather than metric labels unless cardinality is strictly controlled.

05 — management

Operate the monitoring configuration like software

Monitoring configuration grows, accumulates stale dashboards, and can generate operational debt. Keep ownership clear, version rules, test changes where practical, and periodically delete unactionable alerts.

Prefer reusable libraries and conventions so services expose common metrics consistently. This reduces cognitive load for responders who move between systems.

The strongest monitoring strategy therefore has two layers: simple service-level signals that answer 'are users hurting?' and richer internal signals that answer 'why?'.

Small diagnostic example:
250,000 requests / 10 min, 1,250 failures → error rate = 1,250 ÷ 250,000 = 0.5%.
If the allowed error rate is 0.1%, the current error rate is 5× that threshold. That tells you severity; change/dependency/resource metrics help explain cause.
Anti-pattern: page directly on every internal anomaly. CPU at 90% is a diagnostic clue; user-visible failure or an imminent SLO threat is a paging reason.

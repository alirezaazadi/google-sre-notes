why not just go bigger

Power isn't the answer

The chapter opens with a deliberately provocative thought experiment: imagine an infinitely powerful single machine on a network that never fails. Would that be enough for Google's needs? No — and not for a subtle reason, but a physical one: the speed of light itself caps how fast a signal can travel down a fiber link, which puts a hard floor under latency purely as a function of distance. No amount of raw compute power fixes physical distance. And separately, any single-machine design is a single point of failure — unacceptable regardless of how powerful that one machine is.

So the real problem isn't "how do we get a faster machine" — it's "how do we decide which of many machines, in many places, should handle this particular request" — and the chapter is upfront that "optimal" here has no single universal answer. It depends on the level you're looking at (global vs. local), the layer (hardware vs. software), and the nature of the traffic itself.

Two traffic types, two different definitions of "optimal"

At the global level, these two traffic types genuinely want different things — a search request wants the nearest datacenter by round-trip time, an upload wants whichever path currently has spare throughput, even at a latency cost. At the local level, inside a single datacenter, the calculus flips: all machines are roughly equidistant from the user, so the goal shifts to pure resource utilization and keeping any one server from becoming overloaded (that's Chapter 20's focus).

layer 1

DNS load balancing: the cheapest lever, pulled first

Before an HTTP request can even be sent, the client typically has to resolve a domain name via DNS — which makes DNS the very first opportunity to steer traffic. The naive approach — return several A/AAAA records and let the client pick arbitrarily — is trivial to implement but gives almost no real control: each address gets roughly equal traffic regardless of which is actually best for that specific client.

Three problems the "DNS middleman" creates

End users almost never talk directly to Google's authoritative nameservers — a recursive resolver (often run by their ISP) sits in between, and that middleman creates three distinct headaches:

  • Recursive resolution hides the real client. The authoritative nameserver only ever sees the resolver's IP, not the user's — so "route based on shortest distance" ends up optimizing distance to the wrong endpoint. The chapter's fix: the EDNS0 extension, which lets a resolver forward a hint of the client's actual subnet — not yet an official standard at time of writing, but already adopted by major resolvers like Google's own and OpenDNS specifically because the benefit is so clear.
  • One resolver can represent wildly different geography. The chapter's concrete example: a national ISP might run all its nameservers from a single datacenter while still having real network interconnects spread across every metro area it serves — meaning the "optimal" answer computed from the resolver's location can be actively wrong for most of the actual users behind it.
  • Caching makes impact hard to predict. An authoritative reply gets cached and reused by the resolver for as long as its TTL allows, so a single DNS answer might reach one user, or genuinely might reach thousands, with no way to know which in advance.

Google's practical mitigation for the last two: continuously track the approximate user population and estimate the geographic spread behind each known resolver, so routing decisions can be made against real observed behavior rather than resolver identity alone. When a resolver's user base is spread across a huge region, this becomes an explicit trade-off — optimize for the majority, accept a worse outcome for the geographic tail.

"Best location" means more than "nearest"

Distance alone isn't sufficient — the chosen datacenter also needs enough spare capacity to actually absorb the incoming load, and needs to be structurally healthy (no active power or network issues). This is only possible because the authoritative DNS server is integrated directly with Google's real-time traffic, capacity, and infrastructure-health control systems — DNS load balancing isn't a static config, it's a live decision informed by current system state.

DNS load balancing's hard ceiling: DNS replies are capped at 512 bytes by RFC 1035, which bounds how many addresses can fit in a single answer — and that number is nowhere close to the number of actual backend servers available. DNS gets traffic roughly to the right neighborhood before a connection even opens, but it can't be the whole solution — a second layer is required.
layer 2

Virtual IPs: hiding "how many machines" behind one address

A Virtual IP (VIP) isn't bound to any single network interface — from the outside it looks like one ordinary IP, while a network load balancer actually distributes incoming packets across many real backend machines behind it. This is what lets Google add capacity, remove a failed machine, or perform maintenance completely invisibly to users.

Picking a backend without keeping expensive state

The intuitive approach — always send the next request to whichever backend is currently least loaded — sounds ideal, but breaks down for stateful protocols, where every packet in a connection has to keep landing on the same backend. That would require the balancer to track every open connection.

The stateless alternative: derive a connection ID directly from the packet (e.g., a hash of source/destination info) and pick a backend with id(packet) mod N. No per-connection memory required — until a backend fails and drops out of the pool. The moment N becomes N−1, almost every packet's modulo result changes, remapping nearly all active connections to a different backend all at once and forcing a mass connection reset.

sketch — why naive modulo hashing shatters on a single backend failure (original diagram)

Consistent hashing (1997) is the fix: a mapping scheme designed so that adding or removing a backend only remaps the small fraction of connections that were actually assigned to that specific backend, leaving everything else untouched. Google's practical approach layers both: simple connection tracking in the common case, falling back to consistent hashing specifically when the system is under pressure — such as during an active denial-of-service attack, exactly when connection churn is highest and stability matters most.

Actually getting the packet to the backend

Three approaches, in the order the chapter presents their trade-offs:

  • Network Address Translation — works, but requires a connection-tracking table entry per flow, which rules out a fully stateless fallback.
  • Direct Server Response (DSR) — the balancer rewrites the destination MAC address at layer 2 only, leaving IP addresses untouched, so the backend can reply directly to the client without routing the (often much larger) response back through the balancer. Huge savings for typical HTTP traffic where requests are small and responses are large — and it needs zero state on the balancer. The catch: every balancer and every backend must be reachable at the data-link layer, meaning they all have to share one broadcast domain — a constraint Google eventually outgrew entirely at scale.
  • Packet encapsulation (current solution) — wraps the forwarded packet inside another IP packet using GRE, addressed to the backend. The backend strips the outer layer and processes the inner packet exactly as if it arrived directly. This fully decouples balancer and backend — they no longer need to share a broadcast domain, or even a continent, as long as a route exists between them. The cost: GRE encapsulation adds real overhead (24 bytes for IPv4+GRE specifically), which can push a packet's size past the network's MTU and force fragmentation — mitigated within the datacenter by supporting a larger internal MTU, at the cost of requiring network hardware that can actually handle those larger frames.

vocabulary

Machine vs. server — the one distinction everything else depends on

Google draws a hard line between two words people usually use interchangeably:

  • Machine — a physical box (or VM). Just hardware.
  • Server — a piece of software that implements a service. It has no fixed home.

Why bother? Because at Google's scale, no machine is dedicated to a particular piece of software. There's no "the mail server machine." A scheduler called Borg decides, dynamically, which machines run which software, and moves things around as machines fail or load shifts. Once you accept that servers float freely across machines, most of the rest of the chapter is just: which system handles which layer of that floating arrangement?

Physical layout, zoomed out

Machines are grouped into racks (tens of machines), racks form a row, rows form a cluster, a building holds multiple clusters, and nearby buildings form a campus. Within a datacenter, an internal network fabric called Jupiter connects everything at extremely high bandwidth; between datacenters, a backbone called B4 connects campuses globally.

the scheduler

Borg: the thing that decides where software actually runs

Borg is Google's cluster operating system — think of it as the layer that turns "a room full of machines" into "a pool of compute you can hand a program to." (If you know Kubernetes: Borg is its direct ancestor.)

You give Borg a job — could be a long-running server, could be a one-off batch process — made of one or many identical tasks. Borg finds machines with free capacity, starts your tasks there, and then keeps watching them. A crashed task gets killed and restarted, possibly on a completely different machine.

Two details make this genuinely resilient rather than just "auto-restart":

  • Naming survives relocation. If a task can move to a new machine at any time, you can't hardcode its IP. So Borg gives every task a stable name via the Borg Naming Service (BNS) — something like /bns/cluster/user/job/task-number — which resolves to wherever that task currently lives.
  • Placement respects failure domains. Borg won't just pack a job's tasks onto whatever's free — it deliberately spreads them so they don't all share one point of failure, like a single rack's top-of-rack switch.

Borg also enforces resource limits: if a task tries to use more CPU/RAM than it declared, Borg kills and restarts it — the reasoning being a task that crash-loops visibly is better than one silently starving its neighbors.

storage

The storage stack: from raw disk to a global database

Storage is layered, each layer hiding the mess of the one below it:

sketch — the storage stack, bottom to top (original diagram)
  • D — the lowest layer, a fileserver running on nearly every machine. You wouldn't want to use this directly — you'd have to remember which machine holds your data.
  • Colossus — sits on top of D, gives you one cluster-wide filesystem with normal filesystem semantics plus replication and encryption. This is the successor to the original Google File System (GFS).
  • Bigtable / Spanner / Blobstore — database systems built on Colossus. Bigtable is a huge, sparse, sorted key-value store (rows × columns × timestamp) with eventually-consistent cross-datacenter replication. Spanner trades some of that flexibility for real global consistency via an SQL-like interface. Each of these makes a different consistency/performance tradeoff.
plumbing

The rest of the plumbing, briefly

  • Chubby — a lock service, using the Paxos consensus algorithm, used for two main things: distributed locking, and master election (if 5 replicas of a job exist but only one should actually do the work, Chubby is what picks which one).
  • Borgmon — the monitoring layer. It periodically scrapes metrics from every running task, both for real-time alerting and for building historical graphs used in capacity planning.
  • Stubby / gRPC — Google's internal RPC framework (gRPC is its open-source descendant). Even calls that could technically be a local function call are often made as RPCs, because it keeps the door open to move that logic to a different server later without a rewrite.
  • Protocol buffers — the data format carried by those RPCs. Compared to XML: simpler, 3–10x smaller on the wire, 20–100x faster to parse.
  • GSLB (Global Software Load Balancer) — routes traffic at three levels: DNS-level geographic routing, service-level routing, and RPC-level routing within a datacenter — always aiming for the closest datacenter that still has spare capacity.

Tying it together: "Shakespeare," a toy search service

The chapter walks through a hypothetical service that lets you search where a word appears across Shakespeare's works, to show how these pieces cooperate.

Two components: a batch job (a MapReduce: map → shuffle → reduce) that indexes the text once and writes results into a Bigtable, and an always-on frontend that serves user queries against that index.

The N+2 sizing exercise — the part worth remembering

This is a small, concrete preview of the capacity-planning mindset the rest of the book returns to constantly. Say load testing shows one backend task handles ~100 QPS, and peak expected traffic is ~3,470 QPS. Naively that's 35 tasks. But:

  • During a routine rolling update, one task is always briefly unavailable → down to 34 tasks of headroom.
  • If a machine also happens to fail during that same update → down to 35 tasks serving, which is exactly peak load, with zero margin.

So the real answer is N+2: 37 tasks, not 35 — two full tasks of spare capacity, so a routine update and an unrelated failure can happen at the same time without falling behind. The chapter then geo-distributes those 37 across regions matching real traffic split (US, Europe, Asia get N+2; South America deliberately gets only N+1, accepting a small latency risk during that region's own failures in exchange for ~20% less hardware spend there).

The general lesson: "how many do I need" always means "how many do I need if the thing I expect to go wrong (a rolling update) happens at the same time as the thing I don't expect (a random failure)."

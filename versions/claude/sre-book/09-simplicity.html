Chapter 9: Simplicity

"Boring" is a compliment. Every line of code is a liability. And deleting code is one of the most satisfying — and reliability-positive — things an engineer can do.

the tension

Stability vs. agility — the balance SRE is actually managing

The chapter opens with a small but important observation: a software system is only ever perfectly stable if nothing about it ever changes — no new code, no new users, no underlying library updates. That's not a real option. So SRE's actual job, distilled to one sentence, is keeping agility and stability in balance, not maximizing either one in isolation.

Sometimes tilting toward agility is the right call — the chapter's own example is exploratory coding: writing throwaway code with an explicit "shelf life," deliberately skipping heavy test coverage and release rigor, because the code will never touch production or a real user. That's a legitimate, deliberate trade, not sloppiness — it's scoped precisely to code nobody depends on yet.

For the vast majority of production systems, though, the goal is a balanced mix — and the chapter makes a claim that's easy to miss on a first read: reliable process tends to increase agility, not trade against it. Fast, predictable rollouts make it easy to see exactly which change caused a problem, which means bugs get found and fixed faster — freeing developers to spend their attention on functionality and performance instead of firefighting mystery regressions.

the core value

"Boring" is the highest compliment you can pay a system

Software is one of very few domains where "boring" is unambiguously good. You don't want your production system to surprise you — you want it to do the same predictable thing every time, forever. Surprises in production are, in the chapter's framing, SRE's actual enemy.

To reason clearly about where complexity is worth fighting, the chapter borrows Fred Brooks' classic distinction:

  • Essential complexity — inherent to the problem itself, and can't be engineered away. Serving web pages fast is inherently nontrivial; that complexity is baked into the problem statement.
  • Accidental complexity — complexity introduced by the specific tools or choices used to solve the problem, and can be reduced with engineering effort. Writing that same web server in a garbage-collected language can introduce GC-pause complexity that has nothing to do with serving pages per se — it's a side effect of the implementation choice.
What this means day-to-day for an SRE team: push back when accidental complexity creeps into systems you're responsible for, and keep actively hunting for it in systems you already own — it's not a one-time cleanup, it's an ongoing posture.
deleting code

Every line of code is a liability, not an asset

This is the chapter's most quotable — and most counterintuitive to most engineers' instincts — argument. For a service expected to run 24/7, every line of code that exists is something that can eventually break, and someone has to keep understanding, testing, and maintaining it. Code isn't valuable by default; it earns its keep only by actively serving a business goal.

The chapter's real-world stakes example is Knight Capital: a disabled, dead flag path left in production became exactly the kind of "time bomb" this section warns about, and detonated at enormous financial cost when it was inadvertently reactivated. The general point: untested, disabled code paths don't just sit there harmlessly — they're a latent risk waiting for the one condition that flips them back on.

the mindset

"Negative lines of code" as a genuine metric to be proud of

Every line added or changed is a new opportunity for a defect. A smaller codebase is easier to understand, easier to test, and — empirically — tends to have fewer bugs simply by having less surface area for them to hide in. The chapter frames this as a reason to be genuinely skeptical of the reflex to add new features, and treats deleting thousands of now-useless lines as some of the most satisfying, valuable engineering work there is — not busywork, not "cleanup," but a direct contribution to reliability.

design discipline

Minimal APIs and real modularity

The chapter quotes Saint-Exupéry — "perfection is attained not when there is no longer more to add, but when there is no longer anything to take away" — and applies it directly to API design. Fewer methods and arguments means less surface area to understand, secure, and keep backward-compatible forever; a small, tightly scoped API is usually also a signal that the underlying problem is genuinely well understood, not just under-built.

That same instinct scales up from a single API to an entire distributed system:

  • Loose coupling between binaries and their configuration means a bug in one component can be fixed and shipped independently, without dragging the rest of the system along for the ride.
  • API versioning matters because a single breaking API change can force every dependent system to rebuild simultaneously — a direct, cascading reliability risk. Versioning lets consumers upgrade on their own schedule instead of everyone being forced to move in lockstep.
  • No "util" or "misc" binaries. The same reasoning that says "don't write a grab-bag utility class" in object-oriented design applies directly to production services: a well-designed distributed system is made of components each with one clear, well-scoped purpose — not a dumping ground service that quietly accretes unrelated responsibilities.
  • Modularity extends to data formats too — Google's protocol buffers were explicitly designed for backward and forward compatibility, so that the wire format itself doesn't become a coupling point forcing synchronized deploys across every service that speaks it.
releases

Small releases are diagnosable releases

The chapter closes its practical guidance with a direct callback to Chapter 8's high-velocity philosophy: ship one small, understandable change at a time rather than batching a hundred unrelated changes into a single release. If performance regresses after 100 simultaneous changes land together, isolating which one actually caused it is expensive — potentially requiring new instrumentation built after the fact just to untangle the mess.

Analogy the chapter draws directly: this is gradient descent.
Small step → measure → keep if it's an improvement, revert if not → repeat.
Large batched changes are the reliability equivalent of a huge, unmeasured step.

Smaller releases let you move faster with more confidence precisely because each change can be evaluated on its own, in isolation, against the working system — the opposite of what intuition might suggest about "fewer, bigger releases being more efficient."

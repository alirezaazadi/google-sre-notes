Chapter 8: Release Engineering

the role

Release engineering is its own discipline

The chapter's opening move: release engineering isn't "something SREs also do" — at Google it's a distinct job function, sitting between development and SRE, with its own specialized knowledge (source control, compilers, build config languages, package managers, installers). Its whole mandate is: whatever binary and configuration ends up running in production must be traceable back to exactly how it was built — no "unique snowflake" releases, no accidental process drift.

Release engineers build the tools that measure things like release velocity (how long from code change to production), and they set the default best practices — compiler flags, build ID formats, required build steps — precisely so individual teams don't each reinvent (and half-break) their own release process from scratch.

philosophy

Four principles the whole system is built around

1. Self-service

At Google's scale, no central team could possibly gate every team's release manually. So release tooling is built to let each product team run its own release process — deciding their own cadence — with automation handling everything by default, and human involvement only kicking in when something actually goes wrong.

2. High velocity

Counterintuitively, releasing more often is treated as a reliability win, not a risk: smaller, more frequent releases mean fewer changes between any two versions, which makes both testing and troubleshooting easier when something does break. Some teams build hourly and hand-pick which build to actually deploy; others go further with a "push on green" model — every build that passes all tests deploys automatically, no human selection step at all.

3. Hermetic builds

This is the chapter's strictest technical requirement: build the same revision on two different machines, and you must get byte-identical results. That means a build can never quietly depend on whatever compiler or library version happens to be installed on the machine doing the building — every dependency, including the compiler itself, is pinned and versioned as part of the build definition.

Why this matters for bug fixes specifically: if you need to patch something already running in production, you rebuild at the original revision plus just the specific fix — called a cherry pick — using the toolchain version from back then, not today's. Otherwise a routine hotfix could silently pull in months of unrelated compiler or dependency changes.

4. Enforced policy at every gate

Nearly every step is access-controlled and reviewed: who can approve a source change, who can request a build at a given revision, who can approve a cherry pick, who can actually deploy. Every release also gets an automatically generated changelist report — a full account of exactly what changed since the last release — which becomes the first thing an SRE reaches for when a new release starts misbehaving.

the pipeline

From source to running binary: Blaze → branch → test → package → Rapid

sketch — the release pipeline, source to deployed binary (original diagram)
  • Blaze (open-sourced as Bazel) — the build tool. Engineers declare build targets and dependencies; Blaze builds the dependency graph automatically. Every binary carries a build date, revision number, and build ID baked in — so any running binary can be traced straight back to exactly how it was produced.
  • Branching, not merging. Everything lands on the mainline first, but releases don't ship directly from it. Instead, a release branches off mainline at one specific revision, and bug fixes are cherry-picked into that branch individually — never merged back the other way. This guarantees the branch only ever contains exactly what was deliberately chosen, not whatever else happened to land on mainline in the meantime.
  • Testing, twice. Continuous tests run against mainline on every submit, for fast general feedback. Then tests run again on the actual release branch — necessary because a branch with cherry-picks can contain a code combination that has literally never existed anywhere on mainline, so passing on mainline doesn't guarantee passing on the branch.
  • Packaging via MPM (Midas Package Manager) — packages are named, uniquely hashed, and signed. A label (like canary or production) can be moved between package versions, so "give me the canary build" always resolves to whichever build currently holds that label — no one has to track version numbers by hand.
  • Rapid — the orchestrator tying it together, configured via blueprints that define build/test targets, deployment rules, and ownership/ACLs. Because Rapid runs its work as ordinary Borg jobs, it scales to thousands of simultaneous release requests without needing dedicated infrastructure of its own.
deployment

Matching rollout speed to risk, not to convenience

Simple deployments go straight through Rapid. More complex, higher-stakes rollouts use Sisyphus, a general rollout framework with a dashboard for tracking progress and finer control over pacing. The point isn't uniform speed — it's matching rollout pace to how much a mistake there would cost:

Service risk profileTypical rollout pace
Dev / pre-productionHourly builds, auto-pushed the moment tests pass
Large user-facing serviceStart in one cluster, then expand exponentially outward
Sensitive infrastructureRolled out over days, deliberately interleaved across geographic regions
The underlying logic: the riskiest deployments get the slowest, most staged rollouts — not because slower is inherently safer, but because staged rollout is what turns "a bad release" into "a bad release caught in cluster one, before it ever reaches cluster fifty."
config management

Configuration changes are just as dangerous as code changes

The chapter is explicit that configuration deserves the same rigor as binaries — it's a common, underestimated source of production instability. Four different models coexist, each a genuine tradeoff rather than a strictly-better replacement of the last:

  • Configuration lives on mainline directly. Simplest — edit, review, apply. But binary releases and config changes become decoupled, which easily causes drift between "what's checked in" and "what's actually running," since a job has to be explicitly restarted to pick up a change.
  • Config bundled inside the same MPM package as the binary. Simple to deploy (one package, one install) but binds config and binary together tightly — you can't change one without rebuilding both.
  • Config as its own separate MPM "configuration package," linked to a binary release via a shared label. This is the hermetic-build principle applied to configuration: you can now cherry-pick a config-only fix (say, flipping a feature flag) and rebuild just the configuration package — without triggering an entirely new binary build for a change that never touched the code.
  • Configuration read live from an external store (Chubby, Bigtable, etc.) for values that genuinely need to change while the binary keeps running, without a redeploy at all.

There's no single "right" answer among these — project owners pick per-project based on how often their configuration actually needs to change and how tightly it's coupled to a specific binary version.

for everyone else

This isn't just a Google-scale problem

The chapter closes by generalizing deliberately: every organization, regardless of size, faces the same underlying questions — how to version packages, whether to build continuously or periodically, how often to release, what configuration strategy to use. Google's specific tools (Blaze, MPM, Rapid, Sisyphus) exist because off-the-shelf tooling didn't scale to Google's needs — but the policies those tools enforce are worth defining deliberately at any scale, tooling aside.

The chapter's clearest piece of general advice: budget for release engineering from the very start of a project, not as an afterthought bolted on once things are already painful. Retrofitting good release discipline onto an established system is far more expensive than building it in from day one — and it works best when developers, SREs, and release engineers are collaborating throughout, rather than developers "throwing code over the fence" for someone else to figure out how to ship.

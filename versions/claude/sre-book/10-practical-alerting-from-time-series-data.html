Chapter 10: Practical Alerting from Time-Series Data

Inside Borgmon, the system that turned "run a script, check for errors" into "collect everything, compute alerts from history" — and quietly became the ancestor of Prometheus.

the shift

From "run a script and check" to "collect everything, compute later"

Before Borgmon, monitoring at Google looked like most places still look: custom check scripts that individually poll a target, decide pass/fail, and alert — completely separate from whatever tool draws the trend graphs. Borgmon's actual innovation was making the collection of time-series data itself a first-class, permanent thing, and then building a real query/rule language on top of that stored history, instead of throwing away each check's result the moment it ran.

This matters because Prometheus, one of the most widely used open-source monitoring systems today, was directly inspired by Borgmon's model — collect labeled variables, evaluate rules over their history, generate alerts from the same data that feeds dashboards. Understanding Borgmon is understanding the shape of an entire generation of monitoring tools that came after it.

The scale problem this solves: at Google's size, paging a human for a single failed machine is unacceptable noise — one machine failing is a statistical certainty happening constantly, not an event. The system needs to aggregate signals and prune outliers automatically, alerting on high-level service objectives while still preserving the ability to drill into individual components when actually debugging.
instrumentation

varz: the dead-simple export format that made this all possible

Every Google binary exposes an HTTP endpoint (historically called /varz) that just lists its internal counters as plain text — no schema required:

curl https://webserver:80/varz
http_requests 37
errors_total 12

map-valued: http_responses map:code 200:25 404:0 500:12

Adding a new metric to a program is a single line of code. That low barrier to instrumentation was deliberate — and it comes with a real tradeoff the chapter is upfront about: because the metric definition and its use in Borgmon's rules are decoupled (nothing enforces a schema), keeping the two in sync over time requires real discipline, which Google addressed by building separate tooling to validate and generate rules automatically rather than trusting humans to keep them aligned by hand.

Borgmon polls each target's /varz at a set interval, staggering collection across targets so they're not all hit in lockstep. It also records a handful of "synthetic" variables per target automatically — did the name resolve, did the target respond, did the health check pass, when did collection finish — which alone are often enough to write a useful "is this task even reachable" alerting rule.

storage model

Time-series, labels, and the "arena"

Every data point is a (timestamp, value) pair, and every time-series is uniquely named by a set of key=value labels — a labelset. At minimum, a time-series needs: var (the metric name), job (server type), service (a group of jobs serving users), and zone (the datacenter location where it was collected).

{var=http_requests, job=webserver, instance=host0:80, service=web, zone=us-west}

Querying doesn't require every label — dropping instance from that query returns a vector: one row per matching instance. This is the mechanism that lets the same rule work whether there's 1 task or 10,000 — you write the rule once against the labelset shape, and it naturally fans out.

sketch — a labelset query returning a vector across instances (original diagram)

Storage is an in-memory time-series arena — a fixed block of RAM, garbage-collected oldest-first once full. The window of retained data is the horizon, typically sized around 12 hours for datacenter/global Borgmon: enough to debug a recent incident interactively, without the RAM bill of keeping everything forever. Older data gets periodically archived out to a separate, cheaper Time-Series Database (TSDB) for slower historical queries.

~24 bytes per data point → 1M unique time-series, 12h at 1-min intervals, fits in under 17 GB RAM
rules

Borgmon is "just" a programmable calculator over time-series

Rules are algebraic expressions that compute new time-series from existing ones — they can look back in time on one series, or across labels on many series at once, in the same expression. The chapter's running example builds up an error-rate alert from raw counters, step by step:

1. per-task request rate:
  task:http_requests:rate10m = rate({var=http_requests,job=webserver}[10m])

2. sum across tasks in the datacenter (drop the instance label):
  dc:http_requests:rate10m = sum without instance(task:http_requests:rate10m)

3. same idea for error responses, then:
  dc:http_errors:ratio_rate10m = dc:http_errors:rate10m / dc:http_requests:rate10m

Two details worth internalizing, because they explain a lot of real-world monitoring bugs elsewhere:

  • Counters, not gauges, for anything you plan to rate() over. A counter only ever increases, so even if a scrape is missed, the next successful scrape still reflects everything that happened in between. A gauge (current value, can go up or down) silently loses any activity that happened between two samples.
  • Sum the rates, don't rate the sum. Summing individual rates before combining protects the result against a single task restarting (which resets its counter to zero) — that reset would otherwise corrupt a naive "sum first, then compute rate" calculation for the whole aggregate.

There's also a small but genuinely useful naming convention baked into the examples: scope:variable:operation — e.g. dc:http_errors:ratio_rate10m reads as "datacenter-level HTTP errors, expressed as a 10-minute ratio rate." A convention like this makes a large rule library skimmable instead of archaeological.

alerting

From "rule is true" to "a human's pager buzzes"

{var=dc:http_errors:ratio_rate10m,job=webserver} > 0.01
  and by job, error
{var=dc:http_errors:rate10m,job=webserver} > 1
  for 2m
  => ErrorRatioTooHigh
    details "webserver error ratio at %trigger_value%"
    labels { severity=page };

This fires only when both conditions hold — a high error ratio alone isn't enough (that could just mean traffic is very low), and a high absolute error count alone isn't enough either (that could be normal at high traffic). Requiring both filters out a whole category of noisy, technically-true-but-not-actually-urgent alerts.

The for 2m clause exists specifically to fight flapping — a rule that goes true, false, true, false in rapid succession. Requiring the condition to hold continuously for at least two evaluation cycles before actually paging means one missed collection or one brief blip doesn't wake anyone up.

Fired alerts route to a central Alertmanager, which handles the parts that shouldn't live in every individual Borgmon: deduplicating identical alerts arriving from multiple Borgmon instances, suppressing an alert when a related, more-informative one is already firing, and fanning alerts in or out based on their labels. This is also where the Chapter 6 taxonomy actually gets applied in practice — page-worthy alerts go to on-call, important-but-not-urgent ones go to a ticket queue, everything else just feeds a dashboard.

scaling monitoring itself

Borgmon monitoring Borgmon: a hierarchy, not a single collector

A single Borgmon trying to scrape every task of a global service directly would be both a scaling bottleneck and a single point of failure. Instead, Borgmon instances form a hierarchy: typically one Borgmon per datacenter cluster, feeding up into two or more global Borgmon for top-level aggregation (deliberately two-plus, so routine maintenance or an outage of one doesn't blind the whole hierarchy). For very large services, even the per-datacenter layer splits further into pure "scraper" Borgmon feeding a separate aggregation layer.

sketch — the Borgmon aggregation hierarchy, filtered at every tier (original diagram)

Crucially, upper tiers filter what they pull from lower tiers rather than importing every raw per-task series — the global layer builds a local cache of only what's actually relevant at that level, so it doesn't drown in per-task noise it will never need.

the blind spot

White-box monitoring alone can't see what users experience

Borgmon is fundamentally white-box (Ch.6's term) — it inspects internal state, with rules written by people who understand those internals. That transparency is powerful for diagnosis, but it has a hard limit: you can only see the requests that actually reached your instrumentation. A request lost to a DNS failure, or dropped by a crashed server before it was ever counted, is invisible to a purely white-box view — you can only alert on the failure modes you already anticipated.

The fix is Prober — a black-box checker that actually behaves like an external client: makes a real protocol request against a target, validates the response payload (not just "did it respond," but "was the HTML actually correct"), and can export what it finds as its own time-series. Pointing Prober at both the public load-balanced endpoint and individual datacenter backends behind it lets a team distinguish "one datacenter is failing but users are unaffected because traffic failed over cleanly" from "the failure is visible all the way to the edge" — a distinction pure white-box monitoring can't make on its own.

config at scale

Rules as reusable templates, not copy-pasted per team

Borgmon separates rule definitions from the specific targets they apply to, so the same rule set can be reused across many services instead of being hand-copied and subtly diverging each time. Two families of reusable templates emerged in practice: ones that just codify the schema a shared code library already exports (an HTTP server library, an RPC framework — reuse the varz shape, get the rules for free), and ones that encode generic aggregation patterns matching a service's actual topology (task → job → shard → datacenter → global).

That topology modeling isn't arbitrary — the grouping choices are meant to track shared fate: tasks sharing a config file fail together, jobs in a shard share a datacenter's fate, sites share a network's fate. Structuring aggregation around genuine shared-failure boundaries is what makes "which layer is actually broken" a fast question to answer during an incident, instead of a guessing game.

Guarding against config rot: because a rule language this expressive can also become a source of bugs, Borgmon configs get real unit and regression tests — synthesizing fake time-series data to confirm a rule behaves as intended — run continuously before configuration ever ships to production Borgmon instances.

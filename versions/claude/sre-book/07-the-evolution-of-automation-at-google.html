Chapter 7: The Evolution of Automation at Google

Automation is a force multiplier, not a fix — it amplifies whatever direction you point it in, good or bad. Three real case studies trace the path from manual toil to systems that don't need automation at all.

the reframe

Automation is force, not direction

The chapter opens with a warning before it opens with praise: automation multiplies whatever it's pointed at — thoughtless automation creates exactly as many problems as it solves, just faster and at greater scale. The actual goal, ranked above automation itself, is a system that needs neither manual operation nor automation glue at all — an autonomous system that handles the problem internally.

Five separate reasons automation is valuable

  • Consistency. No human, however careful, executes the same 500-step procedure identically every time. A machine does — this is often automation's primary value for well-scoped, well-understood procedures, independent of scale.
  • A platform. Good automation isn't just a script — it's something extensible, reusable across systems, and it centralizes mistakes: a bug fixed once in the platform stays fixed everywhere, instead of needing to be "fixed" in every human's head simultaneously.
  • Faster repairs (lower MTTR). Automated remediation for common faults shortens mean-time-to-repair, and problems caught earlier in their lifecycle are cheaper to fix than the same problem discovered later in production.
  • Faster action. Humans are just slow relative to machines for well-defined actions like failover — requiring a person to click "continue operating" doesn't add safety, it adds latency.
  • Time saving. The most-cited reason, but often the least calculable — because once a task is automated, anyone can run it, not just whoever originally knew the manual procedure. That decoupling of "who can do this" from "who built the automation" compounds in ways a simple time-saved estimate misses.
Joseph Bironas' framing, quoted directly in the chapter: processes that aren't automatable mean you keep needing humans to staff them forever — you're "feeding the machines with the blood, sweat, and tears of human beings."

Each stage is genuinely better than the last, but the chapter is explicit that stopping at "step 4" (automation shipped with the system, but still fundamentally external glue reacting to problems) is settling. case study 1

MySQL on Borg: automating a team out of its own job

Ads' MySQL databases were manually managed and considered "mature" by 2008 — most routine replica-replacement toil was gone. The next ambition was moving MySQL onto Borg (Ch.2's cluster scheduler) for better resource packing. That created a new problem: Borg reschedules tasks constantly — once or twice a week — which is fine for read replicas, but MySQL master failovers were taking 30–90 minutes each, manually.

Manual failover: 30–90 min → best case ~99% uptime (misses the actual SLO)
Error budget required: < 30 seconds of downtime per failover
→ no human-driven process can hit that number; automation wasn't optional

The team built Decider, an automated failover daemon that completed both planned and unplanned failovers in under 30 seconds, 95% of the time. This is the chapter's clearest statement of a broader mindset shift: instead of optimizing to prevent failover, the team optimized to recover from it quickly and automatically — accepting that failure at this scale is simply inevitable, not something to be engineered away entirely.

The payoff compounded: once failover stopped requiring humans, the team had time to automate schema changes too, cutting total Ads Database operational maintenance by ~95% and freeing up ~60% of hardware (via denser bin-packing on Borg). Automating one hard problem bought the time to automate the next one — a virtuous cycle, not a one-off win.

The real cost, stated plainly: this wasn't free. Every application talking to this MySQL setup had to be rewritten with far more failure-handling logic than the MySQL ecosystem normally assumes is necessary — a deliberate trade of application-side complexity for operational simplicity.
case study 2

Cluster turnup: what happens when automation gets orphaned

This is the chapter's cautionary tale, and the most detailed one. Standing up a new datacenter cluster involved dozens of interdependent subsystems (DNS, lock service, storage, compute), each evolving weekly. Early automation was a pile of ad hoc SSH-driven shell scripts — fast to write, and it worked, until it didn't.

The Bigtable wipe — a concrete example of implicit assumptions turning dangerous

A Bigtable cluster had deliberately been configured to skip its first disk for latency reasons. A year later, unrelated automation assumed "first disk unused" meant "this machine has no storage configured — safe to wipe and reinstall." It wasn't. The cluster's data was instantly erased (fortunately there were live replicas). The lesson the chapter draws is specific: automation must never infer safety from an implicit signal — a coincidence in configuration state is not a promise about intent.

Prodtest: turning "is this cluster ready?" into a testable question

The fix was extending Python's unit-test framework to run against real infrastructure: chained tests with dependencies, so one failure would halt anything depending on it and pinpoint exactly what was misconfigured. This finally made "is this cluster correctly configured?" answerable and visible — before Prodtest, nobody could say with confidence why a turnup was taking six-plus weeks.

From detecting problems to fixing them — and a new kind of bug

When leadership demanded five clusters turned up in one week (instead of the usual six-plus weeks each), the team paired every failing test with an automated, idempotent fix — safe to re-run every 15 minutes without risk, so dependency ordering resolved itself naturally as upstream systems became ready. This worked, but introduced flaky tests: the gap between a test running, a fix applying, and a retest created timing windows where not-quite-idempotent fixes could leave the system in an inconsistent in-between state.

The organizational trap: a dedicated "turnup team"

To cut latency further, a specialized turnup team took over running the automation on behalf of every service-owning team. This worked briefly, then quietly rotted — and the chapter is unusually candid about naming exactly why, because the failure was organizational, not technical:

  • A team whose job is "make turnup fast today" has zero incentive to reduce the service-owning team's future technical debt.
  • A team that never runs its own automation has zero incentive to design systems that are actually easy to automate.
  • A product manager whose schedule isn't affected by low-quality automation will always deprioritize automation quality in favor of shipping features.
The general principle: the most functional tools are usually written — and maintained — by the people who actually use them. Separating "who runs the automation" from "who owns the underlying system" breaks that feedback loop, and the automation degrades exactly as fast as the world underneath it keeps changing.

The accidental fix: a security mandate

Ironically, what finally broke the cycle wasn't a turnup redesign — it was a security push to eliminate broad SSH/root access, replaced with an authenticated, ACL-driven RPC service (Admin Servers) with code-reviewed, audited access. That structural change happened to force exactly the right shape of solution: each service team now owned an Admin Server exposing a stable API (turnup/turndown RPCs), while remaining free to change their own internals. Turnup became a Service-Oriented Architecture problem — central automation just called each team's Admin Server once a cluster was "network-ready," and each team stayed responsible for keeping its own corner correct.

case study 3

Borg: from parallel-SSH scripts to a self-repairing "warehouse-scale computer"

The final case study zooms out furthest. Early Google clusters were racks with specific, hand-assigned purposes — "search gets machine x1 once crawl is done with it." Automation started small: Python scripts to restart crashed services, track which service ran where, grep logs over SSH.

The limiting factor wasn't the automation's sophistication — it was that every abstraction was still tied to physical machines. Borg's actual innovation was conceptual: stop treating a cluster as a set of owned machines, and start treating it as a pool of schedulable resources exposed through a central API. That single reframing is what let batch and user-facing jobs share hardware safely, and what turned "a machine died" from an incident into a background statistic.

sketch — the reframe from "owned machines" to "a schedulable pool" (original diagram)

The chapter offers a nice mental model for why this matters: rescheduling a task onto a different machine is really just like a process moving from one CPU core to another — the fact that the new "core" happens to sit across a network link doesn't change the logic. Thought of this way, rescheduling isn't something you'd "automate" so much as a native property the system should just have — the same way you wouldn't build external automation to move a process between cores on a single computer.

The one place the single-machine analogy breaks: a single computer isn't generally expected to survive many of its own components failing simultaneously. A warehouse-scale system must be, because at that scale, failures aren't rare edge cases — they're a statistical certainty happening continuously. That's the real argument for self-repair as a design requirement, not an optional nicety.

the warning

Automation's dark side: skill atrophy and silent scope creep

The chapter draws a direct parallel to aviation and industrial automation: as automation quietly absorbs more and more of the day-to-day operation of a system, human operators lose hands-on practice — and their mental model of "what the system is actually doing" drifts away from reality. When automation eventually does fail, the humans meant to step back in have lost the fluency to do so safely, and often the very manual pathways they'd fall back on no longer even exist.

The Diskerase incident — automation amplifying a single bad assumption, instantly

A concrete, sobering example: decommissioning automation wipes ("Diskerases") the disks of retiring machines, verified by an independent system. One run failed partway through, after the wipe step had already succeeded. On restart-from-scratch, the automation computed "machines still needing Diskerase" — correctly — as an empty set. But that automation treated an empty set as a special sentinel value meaning "everything." Within minutes, nearly every CDN machine across all of Google's colocation facilities was wiped.

What saved the day: good capacity planning meant Google's own datacenters could absorb the load with only a minor latency bump most users never noticed. The actual fix took two days of physical reinstalls, followed by weeks of auditing — adding sanity checks, rate limiting, and making the whole decommission workflow properly idempotent.

The lesson isn't "automation is dangerous, avoid it." It's the opposite of that instinct, stated carefully: at Google's scale, automation and autonomous behavior aren't optional — but every automated system needs the same rigor around edge cases, sentinel values, and rate limits that any other critical production system gets.

for smaller teams

You don't need Google's scale to apply any of this

The chapter closes by heading off an easy misreading: none of this requires Google-scale infrastructure to be worth doing. Automation's value isn't purely a time-saved calculation — its other four benefits (consistency, platform effects, faster repair, faster action) apply at any size. And the highest-leverage moment to think about automation isn't after the fact — it's at design time: shipping fast and iterating rapidly gets you working functionality quickly, but rarely produces a resilient system on its own. Ordinary good software engineering practice — decoupled subsystems, real APIs, minimized side effects — is what actually makes a system automatable (and eventually autonomous) later, without a painful retrofit.

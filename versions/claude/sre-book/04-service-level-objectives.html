vocabulary

SLI → SLO → SLA: three layers, not one word

These three terms get flattened into "SLA" in casual conversation constantly. Keeping them separate is the whole point of the chapter:

sketch — indicator, objective, agreement, each building on the last (original diagram)
  • SLI (indicator) — a directly measured number: request latency, error rate, throughput, availability (fraction of well-formed requests that succeed, sometimes called yield), durability (will the data still be there later).
  • SLO (objective) — a target range for an SLI, shaped like SLI ≤ target or lower ≤ SLI ≤ upper. Note you don't always get to choose the SLI's value — incoming request volume is dictated by users — but you can absolutely set a target for something like average latency, and that target then shapes engineering decisions (buy faster hardware, rewrite the hot path).
  • SLA (agreement) — an SLO plus an explicit consequence for missing it, usually financial (a rebate, a penalty). The quick test for telling an SLO from something people are sloppily calling an "SLA": ask "what happens if we miss it?" No real consequence → it's an SLO. SRE rarely writes SLAs directly (that's a business/legal conversation) but helps define the SLIs an SLA leans on, since a fuzzy measurement guarantees a dispute later.
Google Search has no public SLA — no contract with the whole internet — but it still has very real consequences for unavailability (reputation, ad revenue). SLOs matter with or without a formal agreement attached.
the Chubby story

The danger of being too reliable

This is the chapter's best illustration of why SLOs need to be actively enforced, not just aspired to. Chubby (the lock service from Ch.2) was so reliable in practice that other teams started building on the unstated assumption that it would never go down — creating hidden, unacknowledged dependencies with no fallback path.

The fix was counterintuitive: SRE began deliberately taking global Chubby down on a schedule whenever real failures hadn't already used up its error budget for the quarter — intentionally synthesizing an outage. This flushes out unreasonable dependencies while the fix is cheap and planned, instead of finding them for the first time during a real, unplanned outage.

The general principle: a service that's much more reliable than its stated SLO teaches its users the wrong lesson. Meet the target — don't quietly exceed it forever.
choosing SLIs

Picking the right handful of indicators

Track too many metrics and nothing gets proper attention; track too few and real problems go unseen. The chapter groups services into a few archetypes, each with its own natural SLI set:

System typeWhat it typically tracks
User-facing serving systemsAvailability, latency, throughput — could we respond? how fast? how much load could we take?
Storage systemsLatency, availability, durability — is the data still there when we need it?
Big data / pipelinesThroughput and end-to-end latency — how much data, how long start-to-finish?
All systemsCorrectness — was the right answer returned? (often a data quality concern, not strictly SRE's to fix, but still worth tracking)

Averages lie — use distributions

A single average latency number hides two very different failure shapes: bursty instantaneous load that a per-minute average smooths away, and a long tail of slow requests hiding behind a healthy-looking median. The chapter's example: typical requests finish in ~50ms, but 5% of requests take 20x longer — and an average-only dashboard shows a flat, boring line all day while that tail latency swings wildly underneath it.

The fix is to track percentiles, not just the mean: the 50th percentile (median) for the typical case, and a high percentile like the 99th or 99.9th for a realistic worst case. There's also a user-experience reason to favor high percentiles specifically: people tend to prefer a system that's consistently a bit slower over one that's usually fast but occasionally very slow — high variance is worse than a higher, more predictable baseline. If your 99.9th percentile looks good, the typical case is almost certainly fine too.

Client-side vs. server-side measurement

Server-measured latency can look perfectly fine while users are still suffering — say, from slow client-side JavaScript rendering the page after the server already responded. Some SLIs genuinely need to be measured from the client's vantage point, not just the server's, or you'll miss the exact problems that affect users most.

Standardize your SLI definitions

Once you've decided on a metric, nail down its measurement details once, in a reusable template, rather than re-litigating them every time: aggregation window ("averaged over 1 minute"), which population ("all tasks in a cluster"), sampling frequency ("every 10 seconds"), which requests count ("HTTP GETs from black-box monitoring"), and what "latency" even means ("time to last byte"). This turns every future SLI definition into filling in a blank instead of a fresh debate.

choosing SLOs

Working backward from what users want, not forward from what's easy to measure

The chapter's strongest piece of process advice: start from what users actually care about, even if it's hard to measure, and work backward to a proxy metric — rather than starting from whatever's easiest to instrument and calling that "good enough." The second path quietly optimizes for the wrong thing.

Example SLOs, in increasing specificity:
• 99% of Get RPCs complete in < 100ms
• layered: 90% < 1ms, 99% < 10ms, 99.9% < 100ms
• split by workload: 95% of throughput clients' Sets < 1s; 99% of latency clients' Sets (<1kB payload) < 10ms

That last pattern matters whenever one system serves genuinely different workloads (a bulk pipeline that wants throughput, an interactive client that wants low latency) — a single blended SLO would satisfy neither user well, so define separate objectives per class instead of averaging across incompatible needs.

Five rules of thumb for picking targets

  • Don't anchor on current performance. Adopting whatever the system happens to do today, unreflectively, can lock in a number that only survives through heroics — and can't be improved without a rewrite.
  • Keep it simple. Complicated aggregations obscure real changes in system behavior and make the SLO hard to reason about.
  • Avoid absolutes. "Infinite scale with zero latency increase, always available" sounds appealing and is unrealistic — chasing it burns years and money on marginal gains nobody asked for.
  • Have as few SLOs as possible. Cover the system's important attributes, no more. A useful gut-check: if an SLO never actually wins you an argument about priorities, it's probably not earning its keep.
  • Perfection can wait. Start loose and tighten over time as you learn the system's real behavior — much cheaper than starting too strict and having to walk it back once it turns out to be unattainable.

SLOs as a control loop

Once defined, SLOs aren't just documentation — they close a feedback loop: measure the SLI → compare against the SLO → if it's trending toward a miss, diagnose why → take the corrective action (e.g., add capacity if CPU-bound). Without the SLO as a tripwire, you don't know whether — or when — to act at all.

setting expectations

Two tactics for not overpromising

  • Keep a safety margin. Set a stricter internal SLO than the one advertised externally. This buys room to notice and fix chronic problems before users ever see them, and gives you slack to trade some performance for maintainability later without breaking a public promise.
  • Don't overachieve. This is the Chubby lesson generalized: users build on what you actually deliver, not what you promised. If real performance quietly runs well ahead of the stated SLO, users will silently start depending on that extra headroom — so you either intentionally throttle/take the system down sometimes, or accept that you've effectively raised your own bar without meaning to.
The throughline for the whole chapter: an SLO is a lever for prioritization and a contract with reality, not a report card. Picking one badly (too strict, too loose, too vague, silently over-delivered) has real engineering costs in either direction.

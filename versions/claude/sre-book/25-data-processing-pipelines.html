Chapter 25: Data Processing Pipelines

Why periodic pipelines quietly become fragile as they grow — and Workflow, Google's leader-follower alternative built for exactly-once correctness at scale.

the pattern

Pipelines: reads, transforms, outputs — chained together

A data pipeline is the classic pattern: read data in, transform it, write new data out — usually scheduled periodically via something like cron. At Big Data scale, a single program usually isn't enough, so pipelines become multiphase: several programs chained together, each stage's output feeding the next stage's input. The number of chained stages is called the pipeline's depth — a shallow pipeline might be one program, a deep one can run to hundreds.

the fragility

Periodic pipelines start reliable — and quietly stop being reliable

The chapter's core observation, stated from real accumulated experience: a periodic pipeline, carefully tuned at launch (worker count, run interval, chunking strategy), performs reliably at first — and then organic growth quietly stresses it past that original tuning, and problems start appearing: jobs blowing past their deadline, resource exhaustion, chunks that hang indefinitely.

Uneven work distribution — the "hanging chunk" problem

Big Data's foundational trick is splitting work into "embarrassingly parallel" chunks that fit on individual machines. But chunk size isn't always uniform — if work is partitioned by customer, for instance, some customers' data chunks are naturally much larger than others, and because the customer is the unit of indivisibility, the pipeline's entire end-to-end runtime is capped by whichever single chunk happens to be largest.

The trap in how engineers instinctively respond to a hanging chunk: the "obvious" fix — kill the job and let it restart, on the theory that the hang was probably some nondeterministic fluke — often makes things dramatically worse. Because pipelines typically aren't built with checkpointing, restarting doesn't resume from where the hang occurred — it restarts every chunk from scratch, discarding all the time, CPU, and human effort already invested in that run.
infrastructure friction

Periodic pipelines run as low-priority batch — with real consequences

At Google, periodic pipelines are typically scheduled as lower-priority batch work — a reasonable choice, since batch jobs aren't latency-sensitive the way user-facing web services are, and this lets Borg pack them into whatever capacity is currently unused. But that lower priority carries real, concrete costs: degraded and potentially open-ended startup delays, and — under heavy cluster load — genuine risk of preemption when higher-priority work needs the same resources. Running a well-tuned periodic pipeline successfully becomes a genuine balancing act between paying for guaranteed resources and accepting preemption risk.

The scheduling-interval trap

Delays of a few hours are usually tolerable for a pipeline that runs once a day — but as scheduled frequency increases, average scheduling delay can approach (or exceed) the interval between runs, creating a hard practical floor on how often a periodic pipeline can actually run.

A ~20-minute job scheduled more often than roughly every 40 minutes:
→ runs start overlapping with the still-in-progress previous run
→ failure modes: new runs stack up unprocessed, or worse — the nearly-finished
  current run gets killed to make room for the next scheduled one, halting all progress

Pushing the interval below this effective floor doesn't buy more progress — it actively produces worse outcomes, since the specific failure mode (stacking vs. killing the in-progress run) depends entirely on the batch scheduler's policy, but neither outcome is good.

The monitoring blind spot

The standard periodic-pipeline monitoring pattern is to collect metrics during execution but only report them on completion — which means a job that fails partway through leaves you with essentially no operational visibility into what happened. Continuous pipelines don't share this problem, since their tasks simply never stop running, so real-time telemetry is a natural, built-in part of their design rather than something bolted on after the fact.

the herd problem

Thundering herds and Moiré load patterns

This directly echoes Chapter 24's cron discussion: a large periodic pipeline can spin up thousands of workers simultaneously at the start of each cycle, and if there are too many, or they're misconfigured, or driven by faulty retry logic, the underlying cluster services and network can simply be overwhelmed. It compounds in both directions: no retry logic means dropped work silently never gets redone; naive retry logic means failures compound the overload instead of recovering from it. And the chapter names a very human contributing factor too — engineers with limited pipeline experience often make the problem worse by throwing more workers at a job that's failing to finish on time, which is frequently the opposite of what the underlying bottleneck actually needs.

Moiré load pattern — the subtler version

A related, harder-to-spot problem: two or more independent pipelines running on their own separate schedules can occasionally have their execution windows overlap, momentarily piling onto the same shared resource together — even though neither pipeline, viewed in isolation, looks even close to problematic. This shows up clearly on a stacked usage graph: individually modest, staggered load patterns that occasionally interference-pattern into sharp combined spikes — exactly the kind of on-call pain that's genuinely hard to diagnose from any single pipeline's own dashboard, because the actual cause only exists in the interaction between two systems nobody's monitoring together.

the alternative

Google Workflow: leader-follower, built for continuous processing

When a genuinely one-shot batch pipeline gets pulled by business pressure into needing continuously updated results, teams face an uncomfortable choice: refactor under deadline pressure, or move to a fundamentally different, continuous-processing model. Google built Workflow (2003) specifically to make continuous, large-scale processing tractable — combining the leader-follower distributed pattern with system prevalence (keeping all state in memory, for speed, while durably journaling every mutation to disk) to deliver exactly-once correctness guarantees.

Workflow as Model-View-Controller

The chapter offers a genuinely useful analogy — mapping Workflow onto the familiar UI design pattern:

sketch — Workflow's Task Master / Worker / Controller mapped to MVC (original diagram)

The Task Master (model) holds all job state; for best performance, it typically stores just pointers to work rather than the actual payload, with real input/output data living in a shared filesystem. Workers (view) are deliberately, completely stateless — disposable at any moment, which is exactly what makes the whole system resilient to individual worker failure. The optional Controller handles everything auxiliary to the core pipeline mechanics: runtime scaling, snapshotting, rolling back state, or halting the pipeline entirely for business continuity reasons.

Pipeline depth in Workflow is just a matter of how many task groups the Task Master holds — each group representing one stage, capable of arbitrary operations (mapping, shuffling, sorting, splitting, merging). Workers are self-scheduling — they look for available work of the type they handle and pick it up, rather than being centrally assigned.

correctness

How Workflow actually guarantees exactly-once — a genuinely elegant layered design

The Task Master can't store every detail of pipeline state (it's bounded by RAM), so correctness comes from a stack of independent guarantees rather than one central source of truth:

  • Leases, not locks. A worker acquires a time-bound lease on a work unit and may only commit results for units it currently holds a valid lease on.
  • Unique output filenames per worker attempt. This is the clever piece that solves the "orphaned worker" problem directly: if a worker gets orphaned (its lease expired, but it doesn't know that yet and keeps working), it can keep writing to its own uniquely-named output file harmlessly — it simply can never successfully commit, because another worker now holds the lease. And because every worker's output file is uniquely named, an orphan can never accidentally overwrite or corrupt a valid worker's in-progress output either.
  • Task versioning tied to configuration. Every task carries the ID of the configuration used to produce it. If configuration changes while work is still in flight, workers holding leases issued under the old configuration simply can't commit anymore — guaranteeing everything that successfully commits reflects the current configuration, at the acknowledged cost of some in-flight work being thrown away when a config change lands mid-run.
  • A server token identifying the Task Master itself. This guards against a genuinely subtle failure class: what if the Task Master's network address gets reused by a different Task Master (a config change, a misconfigured load balancer sitting in front of several independent masters, even memory corruption altering an IP)? Both client and server validate this token on every single operation, which prevents a silent, slow-burning corruption where everything looks fine right up until a task ID collision between two different masters actually occurs.

Put together, these compose into what the chapter calls a genuinely layered correctness guarantee: configuration consistency, lease ownership, filename uniqueness, and server identity validation — each one closing a different, independent failure mode the others don't cover.

Why not just use a general-purpose database like Spanner directly? Workflow's power comes specifically from tasks being unique and immutable — even a lease change produces an entirely new task rather than mutating an existing record in place. Trying to replicate this on a general database would mean wrapping every single read in a long-running transaction to get equivalent guarantees — technically possible, but the chapter is blunt that it would be "terribly inefficient" compared to Workflow's purpose-built approach.
disaster resilience

Surviving a whole datacenter going dark

Big Data pipelines need to survive genuinely severe failures — fiber cuts, weather events, cascading power failures that can take out an entire datacenter. Pipelines lacking Workflow's strong system-prevalence guarantees typically just enter an undefined state when this happens, forcing costly, manual, duplicated recovery effort. Workflow's approach: the Task Master journals to Spanner — globally consistent, if comparatively low-throughput — specifically to get global durability, using Chubby (the distributed lock service from Chapter 2/23) to elect which Task Master instance is currently allowed to write, with that election result itself persisted in Spanner.

Because Spanner alone isn't high-throughput enough to serve as the primary pipeline filesystem, globally distributed Workflow deployments run two or more local Workflow instances across distinct clusters, plus lightweight reference tasks mirrored into a global Workflow layer as local work is consumed and completed. If a reference task can't be removed from the global layer, the local Workflow simply blocks until the global layer becomes reachable again — a deliberate design choice that preserves transactional correctness even at the cost of temporarily pausing progress, rather than risking a silent inconsistency.

Automated failover runs through a small helper binary (functioning as the "controller" in the MVC framing) inside each local Workflow — it creates the reference tasks and periodically updates a heartbeat task in the global Workflow. If that heartbeat isn't refreshed within a configured timeout, a different region's helper binary can safely seize the in-flight work described by the reference tasks and continue the pipeline — regardless of whatever actually happened to the original region.

the takeaway

Google's own closing advice, stated directly

Periodic pipelines are genuinely useful — but only for genuinely periodic problems. The chapter's explicit parting guidance: if a data processing problem is continuous, or will organically grow to become continuous over time, don't reach for a periodic pipeline at all — go straight to a Workflow-style continuous architecture instead of retrofitting later, under deadline pressure, exactly when it's hardest to do well.

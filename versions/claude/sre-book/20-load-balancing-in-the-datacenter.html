the ideal, and the waste

Perfect balance is the target — and most approaches fall well short

Inside one datacenter, a client task sends requests to a pool of interchangeable backend tasks implementing some service — typically 100 to 1,000 processes for a mid-sized service, sometimes over 10,000 for the largest. In the ideal case, load spreads perfectly evenly: at any moment, the least- and most-loaded backend consume identical CPU.

Why does perfect balance matter so much? Because a datacenter can only accept traffic up to the point where its most loaded single task hits its limit — every bit of idle capacity sitting on every less-loaded task in that same pool is simply wasted, reserved but unusable. The chapter states this with a concrete example: you might reserve 1,000 CPUs for a service in a datacenter, yet in practice never be able to use more than ~700 of them, purely because of imbalance between tasks — the other 300 sit idle on backends that never get their fair share of traffic.

step 1: health

Before balancing load, you have to know who's actually healthy

Flow control: a blunt first line of defense

The simplest approach: a client tracks active requests per backend connection, and stops sending to any backend once that count crosses a threshold (100 is a common default). This doubles as crude load balancing — an overloaded backend naturally gets avoided as requests pile up against its cap. But it's genuinely blunt: many backends become meaningfully overloaded well before hitting 100 active requests, while others with naturally long-lived requests can hit the cap while still having plenty of real spare capacity — the chapter notes cases where this default limit backfired so badly that every backend appeared unreachable simultaneously, with requests queuing client-side until they simply timed out.

Lame duck state: a much more robust answer

A backend task can be in one of three states from a client's point of view: healthy (serving normally), refusing connections (unresponsive — starting up, crashing, or genuinely down), or lame duck — still listening and still able to serve, but explicitly telling clients "please stop sending me new requests."

sketch — the clean-shutdown sequence enabled by lame duck state (original diagram)

This state propagates fast — typically within 1–2 round trips — even to inactive clients, because Google's RPC layer has idle clients still sending periodic UDP health checks even with no open TCP connection. The real payoff: this makes clean shutdown possible without ever serving an error to a request that was already in flight — essential for routine code pushes, maintenance, and machine failures, none of which should be user-visible events.

It also solves a second, less obvious problem: a backend can accept connections early, during a potentially slow startup/initialization sequence, without pretending it's ready to serve — it simply doesn't leave lame duck state until initialization genuinely finishes, avoiding the extra latency of negotiating a fresh connection right at the moment traffic needs to start flowing.

step 2: subsetting

Why every client shouldn't connect to every backend

Every open connection costs real memory and CPU on both ends (periodic health checks alone aren't free) — and at Google's scale, a naive "every client connects to every backend" design wastes enormous aggregate resources for very little benefit. Subsetting caps how many backends any one client actually connects to.

Picking a subset size (typically 20–100 backends in practice) genuinely depends on your traffic shape: you want a larger subset when clients heavily outnumber backends (otherwise some backends might never receive traffic at all), or when client-side request bursts are common — a large fan-out request concentrated onto a too-small subset can locally overload exactly the few backends that subset happens to include.

Random subsetting: intuitive, and surprisingly bad

The obvious first approach — each client shuffles the backend list once and takes the first N — handles restarts and failures gracefully, but the chapter shows with real simulated numbers just how uneven the resulting load actually is:

300 clients, 300 backends, 30% subset (90 backends/client):
least-loaded backend: 63% of average · most-loaded: 121% of average

same setup, 10% subset (30 backends/client):
least-loaded: 50% of average · most-loaded: 150% of average

The pattern is stark: smaller subsets make the imbalance worse, not better. The chapter's conclusion is blunt — getting genuinely even spread out of pure random subsetting would require subset sizes around 75%, which defeats the entire point of subsetting in the first place.

Deterministic subsetting: Google's actual fix

The real solution restructures the problem: divide client tasks into rounds of subset_count clients each (where subset_count = backends / subset_size). Within a single round, every backend is assigned to exactly one client — no overlap, no gaps (except possibly a partial final round). Each round uses its own random seed to shuffle the backend list differently — critically important, because if every round used the same shuffle, a failed backend's load would only redistribute among the small number of backends sharing its exact subset, compounding badly as more backends in that same subset fail together.

def Subset(backends, client_id, subset_size): subset_count = len(backends) / subset_size round = client_id / subset_count random.seed(round) # different seed per round random.shuffle(backends) subset_id = client_id % subset_count start = subset_id * subset_size return backends[start : start + subset_size]

The result, tested on the same 300-client/300-backend scenario at a 10-backend subset size: essentially perfectly even connection counts across every backend — a dramatic improvement over random subsetting's 50%–150% spread using the exact same subset size.

step 3: picking one

Load balancing policies — actually choosing which backend gets this request

Simple round robin — cheap, and surprisingly costly in practice

Cycle through healthy, non-lame-duck backends in order. Simple, and for years Google's default — but the chapter documents a real-world spread of up to 2x CPU consumption between the least- and most-loaded backend under this policy, driven by four compounding factors:

  • Small subsets amplify uneven client request rates. If clients issuing very different volumes happen to share overlapping subsets, the backends in the busiest clients' subsets end up disproportionately loaded.
  • Wildly varying query cost. The chapter's own figure: the most expensive requests at Google can cost 1000x or more CPU than the cheapest ones — an "all of user X's emails today" query can be trivial or enormous depending purely on how much mail arrived. Round robin has no way to know this in advance and treats every request identically.
  • Machine heterogeneity. Not every machine in a datacenter has the same CPU generation, so the same logical request costs measurably different real resources depending purely on where it lands. Google's fix was a normalized virtual unit — the GCU (Google Compute Unit) — mapping every CPU architecture's performance onto one common scale, so scheduling and reservation math could stay meaningful across heterogeneous hardware.
  • Genuinely unpredictable performance factors. Two concrete examples: antagonistic neighbors — unrelated processes sharing the same machine competing for cache space or bandwidth can swing performance by up to 20%, with effects that cascade (slower outgoing requests → more requests stay "active" → heavier garbage collection); and task restarts — freshly restarted tasks (especially on JIT-optimizing platforms like Java) can need meaningfully more resources for their first few minutes, which Google mitigates by deliberately keeping restarted servers in lame duck state for a "pre-warming" period until their performance actually normalizes.

Least-loaded round robin — an improvement, with a dangerous failure mode

Instead of blind round robin, track each backend's current active-request count and round-robin only among whichever backends currently have the fewest active requests. The intuition: heavily loaded backends tend to have higher latency, so naturally routing away from them should self-correct.

The "sinkholing" trap: if a backend is seriously unhealthy and starts returning 100% errors, those error responses can actually be faster to return than a real successful response would have been (failing fast is cheap). A naive least-loaded policy sees that backend's active-request count staying low — because requests complete so quickly — and interprets that as capacity, routing it more traffic, not less. The fix: count recent errors as if they were still-active requests, so an unhealthy backend gets correctly treated as loaded rather than "fast and available."

Even fixed, least-loaded round robin has two structural limits the chapter is explicit about: active-request count is a poor proxy for real capacity when requests spend most of their life blocked on network I/O rather than actual CPU work (a machine that's genuinely twice as fast might show identical active-request counts to a slower one, since both are mostly just waiting); and each client only sees its own requests to a backend — it has zero visibility into what every other client is simultaneously sending that same backend. In practice, large Google services on this policy still saw roughly a 2x spread — not meaningfully better than plain round robin.

Weighted round robin — the actual solution

This is where the picture changes qualitatively: backends themselves report their observed query rate, error rate, and utilization (typically CPU) in every response — including plain health-check responses. Clients use this real, backend-reported data to maintain a live "capability" score per backend and weight round robin proportionally, with failed requests actively penalizing a backend's score for future decisions.

Why this actually works where the others didn't: it's the only policy using ground-truth information the backend itself reports about its real load and health, rather than a client-side proxy (active request count) that can be misleading. In practice, switching services from least-loaded to weighted round robin drastically shrank the spread between the least- and most-loaded backend — the chapter's own measured before/after data shows the gap collapsing sharply the moment weighted round robin is enabled.

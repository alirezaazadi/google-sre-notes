two flavors of toil

Replication toil, then complexity toil — the predictable arc

Early in a project's life, configuration is lightweight — a handful of INI, JSON, or YAML files. As applications, servers, and variations multiply, what used to be "edit one file" becomes "edit the same setting in five places" — the chapter names this replication toil: the mundane burden of managing config duplicated across a system. It's not unique to huge organizations either — it shows up especially fast in microservice architectures with many independently configured components.

The natural fix — building a configuration language or framework — doesn't eliminate toil, it just changes its shape. Freed from overwhelming duplication, a project's config corpus grows again with renewed energy, and eventually runs into complexity toil: the genuinely frustrating task of untangling emergent, sometimes undesirable behavior from your own automation. This typically shows up once a team crosses roughly 10+ engineers, and compounds with continued growth — the earlier you address it, the better, since configuration complexity essentially never shrinks on its own.

Three broad strategies, in order of preference: remove the configuration altogether where the application can reasonably infer or dynamically compute the answer itself (it may have direct access to information — machine specs, current load — the configuration layer never will); introduce a real configuration language to eliminate duplication if replication toil is the dominant pain; and, once a system is in place, adopt the operational best practices below to actively manage complexity toil going forward.

five pitfalls

How configuration systems consistently go wrong

The chapter's central, hard-won claim: it's difficult to find a popular configuration system that avoids all of the following pitfalls — Google built several internal systems that fell into more than one before arriving at its current understanding.

  • Pitfall 1 — failing to recognize configuration as a programming-language problem. If you're not deliberately designing a language, whatever you end up with is unlikely to be a good one. Programming-language features creep in even when the stated goal was "pure data" — a count attribute meaning "provision more than one of these" is a language feature (it needs an external evaluator) wearing data's clothing. String-interpolation rules that quietly grow into full expression support suffer the same fate — strings that "look like just data" but secretly encode checksums, base64, or structural logic. Even the popular YAML+Jinja combination falls into this trap: each half is excellent alone (YAML for pure data, Jinja for HTML templating), but combined they become genuinely hard for both humans and tools to reason about or analyze.
  • Pitfall 2 — designing accidental or ad hoc language features. Bolting programming constructs onto a simple format piecemeal, over time, tends to produce something more complex — and less expressive — than a language actually designed as a language from the start, riddled with gotchas the original authors never anticipated because they never considered how the features would interact.
  • Pitfall 3 — building too much domain-specific optimization. The smaller a bespoke language's user base, the longer it takes to justify real tooling investment — and engineers are understandably reluctant to invest deeply in learning something with zero applicability outside one narrow domain, with no Stack Overflow answers to lean on when something breaks.
  • Pitfall 4 — interleaving configuration evaluation with side effects. Letting configuration reach out to external systems or out-of-band data (DNS lookups, live VM IDs, "latest build version") during evaluation breaks hermeticity outright — in the worst case, you can't even debug your configuration without actually spending money reserving live cloud resources. The fix: evaluate configuration fully first, expose the resulting pure data for inspection, and only then allow any side effects to occur.
  • Pitfall 5 — reaching for an existing general-purpose scripting language (Python, Ruby, Lua). This looks like a shortcut past the first four pitfalls, but tends to be heavyweight and typically needs intrusive sandboxing to preserve hermeticity — a general-purpose language can touch the local filesystem and network by design, which is precisely the access you don't want a config evaluator to have by default. It also assumes every future configuration maintainer is fluent in that specific language, which won't hold indefinitely.
The chapter's recommendation, given all five traps: use an existing, purpose-built configuration DSL (HOCON, Dhall, Jsonnet, and similar) rather than reinventing one. Even if a DSL initially looks more powerful than you strictly need, that headroom tends to get used eventually — and an in-house style guide can always restrict a language's practical surface area if a team wants tighter guardrails than the language itself enforces.
jsonnet

A quick orientation to the chapter's chosen example language

Jsonnet is a hermetic, open-source configuration DSL — Python-like syntax, object orientation, functional constructs — and is a strict superset of JSON, meaning any valid JSON file is already a valid Jsonnet program that simply outputs itself, with added support for comments and more permissive quoting/commas on top. The chapter is explicit there's no single dominant configuration language at Google or among its readers — Jsonnet was chosen purely as a concrete, illustrative example, and the underlying lessons transfer directly to whatever language a team actually uses.

integration

Wiring a configuration language into a real application

If a configuration language natively outputs the format an application already expects (Jsonnet → JSON, directly usable by anything that speaks JSON, YAML, or HCL), no extra integration work is needed. For a genuinely different target format, the general recipe is: represent the configuration data using the language's own generic primitives (maps, lists, strings — available in essentially any config language); use the language's own constructs to eliminate duplication; then serialize to the actual required output format, reusing an existing serializer where one exists (Jsonnet's standard library already emits INI and XML), falling back to basic string templating only as a last resort for formats that genuinely resist structured representation (a raw Bash script, say).

Once a language can drive one application, it can often drive several simultaneously from the same source — defining a port number exactly once and generating both an Nginx config and a matching Terraform firewall rule from it, for instance, or configuring monitoring dashboards, retention policies, and alert routing from the same underlying files. Configuration can nest too — a Cassandra config embedded inside a Deployment Manager config, itself embedded inside a Kubernetes ConfigMap — and a good language handles the resulting string-quoting gymnastics cleanly rather than leaving it to the author.

worked example

Kubernetes: YAML's real ceiling, and what Jsonnet buys you past it

Kubernetes deliberately ships with no bundled configuration language at all — not even an ad hoc one. Simple deployments get by fine on plain YAML; larger ones typically reach for something like Jsonnet once genuine abstraction becomes necessary. YAML's own abstraction facility — anchors — is rarely useful in practice and isn't even supported by Kubernetes itself, so replicating a Kubernetes object four times with minor variations in practice means four nearly-identical YAML files, with the actually-important differences buried in a sea of duplicated boilerplate.

The chapter's worked Jsonnet solution defines one abstract template (MyTemplate) with a required tier field — deliberately left unset via Jsonnet's error construct, so any attempt to instantiate the template without overriding tier fails loudly at evaluation time, functioning much like a pure-virtual method in an object-oriented language. Four separate, short instance files each override just tier (and, where needed, namespace or an extra label) — with the double-colon :: syntax marking tier itself as a hidden field, present for internal template logic but never actually emitted into the final JSON Kubernetes would otherwise reject as an unrecognized property.

The key advantage over a plain function call: templates let you override any field from the parent, not just parameters explicitly exposed by a function signature. A specific instance can reach in and override something normally considered "too low-level" to parameterize — session affinity, say — without the base template needing to have anticipated that override in advance. This is the same "escape hatch for power users" philosophy from Chapter 14, made concrete: the common case stays simple, and the uncommon case still has a clean way to reach past it.

Abstraction like this pays off in two recognizable patterns: a single team maintaining near-identical configuration variants across environments (prod/stage/dev/test) or geographies, and an infrastructure team maintaining a reusable template for a shared component (a caching layer, an API-serving framework) that individual application teams instantiate and lightly customize for their own specific needs.

in-house apps

Designing a custom application to coexist cleanly with a config language

The chapter's governing split: let the configuration language handle the language problem, and let your application handle everything else. Concrete, transferable recommendations:

  • Consume a single pure-data file — let the config language itself handle splitting configuration across multiple source files via imports, so the application only ever needs to parse one final, merged artifact.
  • Represent named collections as objects keyed by name, not arrays of objects with a name field. {"cat": {...}, "dog": {...}} beats [{"name": "cat", ...}, {"name": "dog", ...}] — the object form lets entities be referenced directly by name (animals.cat) rather than through a brittle numeric index that silently breaks if ordering ever changes.
  • Group configuration by functional relationship, not by entity type, at the top level. A structure like {"pot_assembly1": {"pot": {...}, "lid": {...}}} keeps logically related pieces together in one subtree — which is exactly what lets the configuration language apply abstraction along real functional boundaries, rather than fighting an arbitrary type-based grouping that splits related concerns apart.
  • Keep the data representation itself simple. Don't embed language-like features into the data format (that's Pitfall 1 again, one layer down) — doing so forces users to guess whether a given abstraction belongs in the data or in the surrounding language, which is pure confusion for no real benefit. Don't over-engineer around verbosity either — a config language can absorb that cost far more gracefully than a hand-rolled data-format shortcut can. And avoid interpreting custom string-interpolation syntax inside your application when you can possibly avoid it — sometimes it's genuinely unavoidable (describing post-generation actions like alerts or handlers), but the language should be doing as much of the language-level work as it possibly can.
Don't use the configuration language to paper over an inconsistent underlying model. If your data model has awkward naming, mismatched plurals, or genuine mistakes, fix those in the model itself — patching them over at the configuration-language layer just relocates the inconsistency rather than removing it, and risks making things worse if the underlying model changes shape later.

The chapter is direct that configuration changes tend to dominate real outage root causes over time — which makes validating generated configuration a genuine reliability practice, not just hygiene. Syntactic validity alone (does the JSON parse?) catches very little; real value comes from schema validation plus domain-specific checks — required fields actually present, referenced filenames actually existing, numeric values within sane bounds. JSONSchema works directly against Jsonnet's JSON output; applications built on Protocol Buffers get validation nearly for free, since generating the canonical proto JSON form and deserializing it will itself surface most structural problems. Critically: never silently ignore unrecognized field names during validation — an unexpected field is very often a typo, and catching it early (ideally in a precommit hook, not after deployment) is exactly the kind of cheap, high-leverage check worth automating.

operating it

Treating configuration like the software it actually is

  • Version shared libraries deliberately. A breaking change to a widely-used template library forces a real choice: force a synchronized global update across every consumer (often organizationally infeasible), or version the library so different consumers can migrate independently — accepting that consumers who stay on an older version accumulate real technical debt they'll eventually have to pay down. Most config languages, Jsonnet included, don't natively support versioning — a simple directory-per-version convention in the import path does the job in practice.
  • Check configuration into real source control. This directly delivers the change-history and easy-rollback properties Chapter 14 called for, plus a genuine bonus: code review becomes possible for configuration changes the same way it's standard practice for application code.
  • Invest in tooling — style enforcement, linting, editor integration. Post-write and precommit hooks that run formatters and linters automatically keep quality consistent across every author, without relying on individual discipline alone.
  • Write real unit tests for shared template libraries. A Jsonnet test file can import the library under test, exercise it against representative inputs, and assert on the resulting output using assert or the standard library's assertEqual (which usefully reports the actual mismatched values on failure) — with community-maintained frameworks like jsonnetunit available for running a full structured suite rather than aborting at the very first failing assertion.
when to evaluate

Early, at build time, or at runtime — three points on a real tradeoff

Because a properly hermetic configuration language always produces the same output for the same input, generated JSON is fully interchangeable with the Jsonnet source that produced it — meaning you have real freedom in when you choose to actually run the evaluation.

WhenProsCons
Very early — check in the generated JSON alongside sourceReviewers can sanity-check that a refactor genuinely didn't change output; full line-level audit history at both levels; no runtime evaluation risk or binary-size costGenerated JSON isn't always readable (long embedded strings); may be unsuitable to commit at all (too large, contains secrets); concurrent edits across separate source files can collide into painful JSON merge conflicts
Middle — evaluate at build time, embed the resulting JSON in the release artifactControls runtime complexity, binary size, and risk exposure without rebuilding JSON on every pull request; zero risk of source and generated output drifting apartA more complex build pipeline; harder for a reviewer to directly see the concrete effect of a change
Late — evaluate at runtime, linking the language directly into the applicationSimplest to set up — no separate build step; supports genuinely dynamic, user-supplied configuration at runtimeLarger runtime footprint and risk surface; configuration bugs surface at runtime, which is the most expensive place to discover them; untrusted input needs real, deliberate sandboxing (see below)

Google's own general preference leans toward the build-time middle ground for exactly the reasons in that row. Which approach fits depends heavily on your actual deployment shape — a purely local command-line tool (like ksonnet) can safely link the evaluator in-process, since the code only ever runs on its own author's machine; Box.com's infrastructure instead uses Git hooks that act only on already-generated JSON checked into the repo, specifically to avoid ever running Jsonnet server-side; a server-side deployment daemon like Helm or Spinnaker, by contrast, has little choice but to evaluate configuration at runtime on the server — which is precisely where the next section's precautions become essential.

abusive configuration

An infinite loop is the easy failure mode — the real danger is subtler

Unlike a long-running service, configuration evaluation is supposed to terminate quickly with a concrete result. Bugs — or deliberate attacks — can violate that assumption. The chapter's simplest illustration, a trivially non-terminating recursive Jsonnet function, makes the point obvious; a similarly simple function that keeps appending to an ever-growing list makes the unbounded-memory version of the same problem just as easy to write.

Restricting the language to guarantee termination (removing Turing completeness) doesn't actually solve this. A program can terminate in the formal sense while still consuming an absurd, practically-infinite amount of time or memory before it does — the chapter's example: naive recursive doubling that's entirely well-defined and guaranteed to halt, yet still explodes combinatorially in practice. This exact class of attack — the "billion laughs attack" — is well known even against supposedly inert, non-Turing-complete formats like plain XML and YAML, via deeply nested entity or anchor expansion.

How much this actually matters depends heavily on trust level. A command-line tool that a developer runs locally to build and deploy their own Kubernetes objects is evaluating fully trusted code — accidental non-termination is rare, and a stray Ctrl-C is a perfectly adequate mitigation; accidental memory exhaustion is genuinely unlikely in that setting. A server like Helm or Spinnaker that accepts arbitrary configuration code from end users and evaluates it live inside a request handler is a fundamentally different, much riskier situation — exactly the setup a real denial-of-service attack could exploit to tie up request handlers or exhaust server memory.

For that untrusted case, the chapter's concrete recommendation is real sandboxing — running the evaluator in a separate process under a resource limit (ulimit or the equivalent on non-Unix systems), typically by forking to the command-line executable rather than linking the language directly into the request handler. Done this way, a runaway configuration fails safely within its resource budget and reports the failure back to the end user, rather than silently degrading the whole service for everyone. Using a memory-safe native implementation of the language (the chapter mentions Go's native Jsonnet implementation specifically) adds a further layer of defense against classic memory-safety exploits in a C++-based evaluator.

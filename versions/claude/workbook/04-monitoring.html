the five jobs

What monitoring is actually for

The original SRE book named the same five jobs monitoring exists to do — this chapter takes each one seriously as a genuine, distinct design constraint, not just a list: alert on conditions needing attention, help investigate and diagnose issues, visually display system state, surface long-term trends for planning, and let you compare behavior before/after a change or between experimental groups. Different systems weight these five differently — which is exactly why "which monitoring system should I use" doesn't have one universal answer.

choosing a system

Four features worth weighing deliberately

Speed

Data freshness directly determines how fast you can be paged — and stale data has a subtler danger too: during active incident response, if too much time passes between taking an action and seeing its effect reflected in monitoring, you can wrongly conclude a fix did nothing, or infer a false correlation between unrelated events. The chapter's rough rule of thumb: data more than 4-5 minutes stale can meaningfully hurt incident response speed. Separately, query speed matters too — a monitoring system that precomputes derived time series from incoming data, rather than tallying raw data fresh on every query, keeps dashboards responsive even under heavy historical queries.

Calculations

At minimum, retain data across multiple months — without that horizon, you can't see genuine long-term trends like organic growth. Aggregated summary data is usually enough for capacity planning, but keeping full granular detail helps answer questions like "has this exact anomaly happened before" — at real storage and retrieval cost. The chapter reinforces a strong preference for monotonically incrementing counters over raw gauges (echoing Chapter 10 of the original SRE book) — counters let you compute clean windowed rates, including the longer windows (up to a month) that SLO burn-rate alerting depends on. And percentiles genuinely matter over averages: a system that can compute p50/p95/p99 directly tells you whether 50%, 5%, or 1% of requests are slow — an arithmetic mean can only tell you "somewhat slower," with zero information about how the slowness is actually distributed.

Interfaces

Different audiences genuinely need different views of the same underlying data — an executive dashboard and an SRE's debugging dashboard shouldn't look identical, but should stay internally consistent in how they present comparable data so nobody has to re-learn a new visual language for every service. Real-time ad hoc drill-down — slicing by machine type, server version, request type on demand — is what actually lets you spot correlations while they're still fresh and relevant, not after the fact.

Alerts

Multiple severity levels enable genuinely proportional response — a low error rate sustained for an hour might just warrant a ticket, while a 100% error rate is an immediate page. Suppression is explicitly called out as essential, not optional: if every node hits the same global error spike simultaneously, you want one alert for the aggregate condition, not one per node flooding the channel; and if a known dependency is already alerting, your own service's downstream symptom shouldn't independently re-alert on top of it. Just as important: suppressed alerts need to reliably un-suppress once the underlying event actually clears, or you risk silently missing a genuine new problem hiding behind stale suppression state.

logs vs. metrics

Two genuinely different data sources, each with a real, distinct role

LogsMetrics
GranularityHighly detailed, per-eventAggregated, coarser
FreshnessInherent delay between event and visibilityNear real-time
Best forRoot-cause investigation, ad hoc queries, detailed batch reportsAlerting and dashboards — fast notification when something's wrong
Typical stackBatch processing (e.g. Cloud Dataflow), ad hoc query (BigQuery), reporting (Data Studio)Purpose-built real-time monitoring system
The chapter's clear default guidance: use metrics for alerting and dashboards — their real-time nature means engineers get notified fast — and use logs to actually find root cause once you're already investigating, since the fine-grained detail you need for that usually isn't (and often shouldn't be) captured as a metric. Resist the temptation to build one-off, ad hoc log-based alerts for rare exceptional events — instead, increment a counter metric when the event happens and alert on that counter. This keeps every alert definition in one consistent, centrally manageable place instead of scattering alert logic across two different systems.
three case studies

Real decisions about where data should actually live

1. Moving information from logs to metrics — App Engine's HTTP status codes

HTTP status codes mattered enormously to App Engine customers debugging their own errors, but only existed in logs — the metrics dashboard showed just one global blended error rate, with no breakdown by actual cause. Debugging meant manually eyeballing a graph for an anomaly, then grepping raw log files hoping to correlate a specific error line back to that spike — slow, and genuinely hard to tell if any single logged error was rare or systemic.

Fix: export the HTTP status code as a metric label — requests_total{status=404} vs. requests_total{status=500}. Since the space of realistic status codes is small and bounded, this didn't blow up metric cardinality into something impractical. Outcome: graphs could now show separate lines per error category, customers could form real hypotheses directly from the exposed codes, and the team could set genuinely different, more accurate alert thresholds for client-caused (4xx) versus server-caused (5xx) errors instead of one blended threshold covering both.

2. Improving both logs and metrics together — an Ads SRE team's brittle scripts

A team running ~50 services across multiple languages used logs as the canonical SLO-compliance source — but each service needed its own hand-maintained, highly specific processing script to decide what actually counted as an error:

IF status in (500,599) AND 'SERVER ERROR' field populated
AND no DEBUG cookie AND URL doesn't contain '/reports'
AND exception != 'com.google.ads.PasswordException'
THEN increment error counter

These scripts were brittle and hard to maintain, and — worse — used data the metrics-based alerting system had no access to, so alerts frequently fired without actually corresponding to real user-facing errors, forcing an explicit manual triage step on every single alert before anyone could act on it.

Fix: build a shared library, hooked directly into each application framework's own request-handling logic, that decides at request time whether an error is genuinely user-impacting — then writes that same decision simultaneously to both logs (with full context for debugging) and metrics (for alerting), guaranteeing the two stay consistent by construction rather than by separately-maintained parallel logic. Outcome: a uniform control surface reused across all ~50 services eliminated the custom per-service log-processing code entirely, and — because alerts were now directly tied to real SLO impact — false positives dropped sharply, since "the alert fired" and "a user was actually affected" became the same statement by design.

3. Keeping logs as the data source — when a metric genuinely doesn't fit

An SRE team investigating incidents routinely needed to look up specific affected entity IDs to assess user impact and find root cause — but unlike the App Engine status-code case, entity IDs could take on millions of distinct values, making them fundamentally impractical as a metric label (cardinality explosion). Each incident required assembling a one-off log query live, under time pressure, adding real minutes to every incident response.

Fix: rather than force a metric where one genuinely didn't belong, the team wrote a reusable script for the recurring log query and documented exactly which script to run directly inside the alert email itself — ready to paste into a terminal the moment an alert fires. Outcome: the cognitive overhead of constructing the right query from scratch under pressure disappeared, results came back faster (though still not as instantly as a true metrics-based lookup), and the approach left room to later automate the query to run immediately on every alert, or poll on a regular interval for semi-fresh results in between.

The throughline across all three: the right answer isn't "always prefer metrics" or "always prefer logs" — it's asking honestly whether the data in question can be practically bounded as a metric label at all, and whether alerting speed or investigative depth matters more for that specific piece of information.
running it well

Managing your monitoring system like the production service it is

  • Treat configuration as code. Store monitoring config in version control for the same reasons you'd version anything else — change history, linked task-tracking references, easy rollback, lint checks, and enforced code review. Prefer intent-based configuration (a config file the system reads) over a pure web UI or CRUD API, since the former is what actually plays nicely with version control in the first place.
  • Encourage consistency across teams — but don't force it rigidly. Google's own evolution converged on a single, centrally-run monitoring framework specifically because it means engineers ramp up faster switching teams, and cross-team debugging gets easier when everyone's dashboards share a common shape and are centrally discoverable. If every service exports a common baseline of metrics automatically (via a shared instrumentation library), every new component gets basic monitoring coverage for free, with zero extra setup effort — usable even by non-engineering teams.
  • Prefer loose coupling between components. Collection, storage, alerting, and visualization should ideally be separable, swappable pieces behind stable interfaces — not one tightly fused monolith. The chapter's own concrete example: when Google migrated from Borgmon to Monarch, dashboarding was deliberately pulled out into its own separate service (Viceroy, from Ch.31 of the original SRE book) — decoupling it meant Monarch itself needed fewer functional requirements, and users could view graphs sourced from *both* the old and new monitoring systems simultaneously, enabling a genuinely gradual migration instead of a risky flag-day cutover.
metrics with purpose

Beyond your SLI dashboard: what actually helps you diagnose "why"

SLI metrics tell you that you're violating an SLO — they rarely tell you why. The chapter recommends four specific categories of supplementary metric, each aimed at closing that gap fast during a real incident:

  • Intended changes. Track binary version, active command-line flags (especially any used as feature toggles), and dynamic config version — or at minimum a last-built/packaged timestamp if nothing is cleanly versioned. Being able to glance at a graph and immediately correlate an outage with a specific rollout beats manually trawling CI/CD logs after the fact.
  • Dependencies. Export request/response size, latency, and response code for every direct dependency — mapped onto the Four Golden Signals, broken down further by response code, RPC method, and peer job name. Ideally instrument this once, in the shared RPC client library itself, so every dependency gets this coverage automatically rather than requiring every team to remember to add it manually. A specific, tricky case worth naming: dependencies exposing one single generic RPC (a bare "Get" or "Query") for many different real operations hide their true signal behind that one opaque interface — you'll see aggregate latency variance and error rates with no way to tell which underlying operation is actually failing, unless you either export more granular metrics that unpack the request payload, or push the dependency's own owners to expose a properly split-out API.
  • Saturation. Track every resource the service depends on — hard-limited ones (RAM, disk, CPU quota) and softer ones without a clean ceiling (open file descriptors, active thread-pool threads, queue wait time, log volume) alike. Language-specific additions matter too: JVM heap and metaspace size (plus GC-specific metrics depending on collector), goroutine count in Go. Alert not just on hard breach, but on approaching a threshold where performance measurably starts to degrade before outright failure — and track every resource for capacity planning purposes even when it's currently well-managed and boring.
  • Status of served traffic. Break traffic down by response code even when most codes don't individually justify their own alert — some are triggered purely by client misbehavior, and having the full breakdown available is what lets you actually distinguish "clients are sending bad requests" from "we're the ones failing." If you enforce rate limits or quotas, separately track how many requests were denied for exceeding them.
Every exported metric should serve a genuine, specific purpose. Don't export something just because it happens to be easy to generate. A good alerting metric should move dramatically only when the system is genuinely unhealthy, and stay flat during normal operation — noisy metrics that wobble under perfectly normal conditions make poor alert material. Debugging metrics, by contrast, don't need that same discipline — their whole job is illuminating what's happening once an alert has already fired, which is a fundamentally different design goal from the alerting metric that triggered the page in the first place.

A genuinely useful postmortem habit the chapter suggests directly: after any real incident, explicitly ask "which additional metric, had it existed, would have let us diagnose this faster?" — turning every incident into a concrete, prioritized backlog item for monitoring coverage, rather than a one-off lesson that fades from memory.

testing monitoring

Monitoring code deserves the same rigor as application code

Monitoring and alerting logic should ideally face the same testing discipline as any other code — but the chapter is candid that broadly-adopted tooling for this is still immature industry-wide. Google's own internal approach: a domain-specific language for generating synthetic time series, paired with assertions checked against the resulting derived time series or against a specific alert's firing status and label values.

Where synthetic testing genuinely isn't feasible for some stage, the chapter's fallback is refreshingly concrete: stand up a small running system that exports simple, well-known metrics (request count, error count) purely to validate that your derived time series and alert rules behave as expected against real, if synthetic, traffic. This matters because alerting rules routinely sit untouched and unfired for months or years after being configured — you genuinely need real confidence that when a threshold is finally crossed for real, the right engineer gets a notification that actually makes sense to them, not a guess made once at config time and never verified since.

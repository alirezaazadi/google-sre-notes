the premise

No single tool stabilizes load — it's always a combination

This chapter extends Chapters 19–20 of the original SRE book with concrete, real-world detail, centered on Google Cloud Load Balancer (GCLB) as a working example — though the chapter is explicit that its lessons generalize to essentially any large-scale load balancer. Google deliberately avoided DNS-based load balancing for GCLB specifically because it depends on client cooperation to properly expire and refetch DNS records — a real, endemic weakness covered in the original book's Chapter 19. Instead, GCLB is built on anycast: routing clients to the topologically nearest cluster via BGP, using a single virtual IP, which both improves latency and lets DNS record TTLs be set much longer.

the architecture

Anycast, Maglev, GSLB, and the GFE — four layers, each with a job

Plain anycast has two real weaknesses: too many nearby users can overwhelm one frontend site, and BGP route recalculation ("flapping") can reset in-progress TCP connections when a user's traffic suddenly gets rerouted to a different frontend mid-session.

Stabilized anycast — the fix. Google's custom load balancer, Maglev, maintains a mapping from client IPs to their actual closest frontend site. If a Maglev machine receives a packet for a client that's really closest to a *different* site, it forwards that packet to a Maglev machine at the correct site instead of processing it locally — preserving session continuity even when BGP routing briefly disagrees with the "true" nearest site.

Maglev itself distributes incoming packets evenly across a pool of machines via Equal-Cost Multi-Path (ECMP) forwarding — meaning capacity scales simply by adding more Maglev machines, and redundancy is modeled as N+1 rather than the traditional active/passive 1+1 pairing most hardware load balancers use. It uses consistent hashing plus a connection-tracking table (keyed on the packet's 5-tuple: source/destination address, source/destination port, protocol) to route a packet to the same backend as previous packets in that connection, without needing to share connection state across machines — letting Maglev scale by raw packet rate rather than by connection count.

GSLB (Global Software Load Balancer) sits above Maglev, balancing live traffic between entire clusters — matching demand to available capacity and transparently draining traffic away from failed clusters. GFE (Google Front End) is typically the first Google server an HTTP(S) request actually touches: it terminates the client's TCP/SSL session, inspects the HTTP header and URL path to decide which backend service should handle the request, then re-encrypts and forwards it. GFEs continuously health-check their own backends, and use "lame duck" mode (from Chapter 20 of the original SRE book) to gracefully retire a backend — continuing to serve in-flight requests while failing new health checks — so updates never disrupt an active user request. GFEs also maintain persistent connections to recently active backends specifically to avoid paying fresh connection-setup latency on every new request.

sketch — the request path through GCLB's layers (original diagram)

To minimize latency specifically, Maglev and GFE are pushed to the very edge of Google's network — SSL is terminated as close to the user as physically possible, since negotiating HTTPS costs two full round trips, and requests then travel over already-established, long-lived encrypted connections deeper into the network from there. Combined with staged canarying — deploying a new version to a small server subset first, gradually increasing traffic while watching for regressions — this architecture is what lets GCLB offer a 99.99% availability SLA.

case study 1

Pokémon GO: 50x over the most optimistic load estimate

Niantic's 2016 launch was, by the chapter's own account, wildly more popular than anticipated — load-tested for up to 5x their most optimistic traffic projection, the actual launch requests-per-second rate hit nearly 50x that estimate. Compounding the raw volume challenge: the game world is globally shared and highly interactive, requiring near-real-time state updates distributed to every nearby player simultaneously.

Before GCLB: a fragile pre-launch architecture

At launch, Pokémon GO used Google's regional Network Load Balancer (NLB) to route traffic into a Kubernetes cluster, with Nginx pods acting as Layer-7 reverse proxies handling SSL termination, HTTP buffering, and routing to application backends. This had real structural weaknesses: SSL termination this far from the edge meant two full round trips before a request even began real processing; buffering HTTP requests from slow-sending clients caused resource exhaustion on the proxy tier; and low-level attacks like SYN floods couldn't be effectively absorbed by a purely packet-level proxy.

The migration, and the cascade it triggered

A large SYN flood attack made migrating to GCLB an urgent priority, undertaken jointly by Niantic and Google's CRE/SRE teams. The initial cutover, during a traffic trough, was unremarkable — but as traffic climbed back toward peak, both companies discovered real client demand was actually 200% higher than anything previously observed. Niantic's frontend proxies simply couldn't keep pace with inbound connections — and refused connections weren't even visible in existing request monitoring, so the true scale of demand stayed hidden until backends themselves started failing.

A textbook cascading failure followed, and it compounded in a specific, ugly way. Overloaded backends didn't fail fast — they got extremely slow, so requests began timing out at the load-balancing layer instead of being cleanly rejected. The load balancer's own retry logic then added more load on top of an already-struggling backend. This retry storm stressed the GFE's SSL client code trying to repeatedly reconnect to unresponsive backends hard enough to trigger a severe GFE performance regression — cutting GCLB's worldwide capacity roughly in half, for every other GCLB customer, not just Pokémon GO.

On top of that, the Pokémon GO app's own retry strategy — a single immediate retry, then constant backoff — meant that whenever the backend briefly returned a burst of fast errors (say, during a shared backend restart), client retries synchronized into a genuine thundering herd. The resulting spikes hit 20x the previous global peak RPS.

The response and the long-term fix

Google's on-call Traffic SREs isolated the GFEs serving Pokémon GO traffic into their own dedicated pool (protecting every other GCLB customer from the collateral damage), enlarged that isolated pool until it could absorb peak traffic despite the ongoing GFE regression (which shifted the bottleneck back to Niantic's own struggling backend), and — with Niantic's explicit agreement — applied an administrative rate limit specifically on Pokémon GO traffic, deliberately containing demand long enough for Niantic to stabilize and scale up properly.

Afterward, Niantic added jitter and truncated exponential backoff to its client retry logic — directly defusing the synchronized-retry thundering herd. Google, in turn, learned to treat GFE backend behavior itself as a potential major source of systemic load, adding qualification and load-testing practices specifically to catch GFE degradation triggered by slow or misbehaving backends before it ships. Both companies drew the same final lesson: measure real client-side demand as close to the client as possible — had that 200% gap been visible ahead of time, Niantic's resources could have been scaled up preemptively, before the cutover, rather than discovered live under fire.

autoscaling

A powerful tool that's genuinely easy to misconfigure

Unhealthy machines quietly break the average

Standard autoscaling averages utilization across all instances, assuming they're roughly homogeneous — but instances stuck starting up, warming up, or wedged in a "zombie" non-serving state still count toward that average, silently masking real need for more capacity. Three combinable fixes: autoscale using a capacity metric observed directly by the load balancer (which naturally discounts unhealthy instances); wait for new instances to genuinely stabilize before counting their metrics at all (a defined "cool-down" period); and pair autoscaling with autohealing, which monitors instance health and automatically restarts anything unhealthy — with enough recovery time built in for the restarted instance to actually become healthy again before being judged.

Stateful systems need different tools than horizontal scaling

If a stateful system routes every request in a session to the same specific backend, simply adding more instances (horizontal scaling) doesn't relieve pressure on an already-overburdened pathway — intelligent, task-level routing (consistent hashing) that actually redistributes load is the better fit. Vertical autoscaling can help absorb short-term hotspots in a stateful system, used carefully — since it's typically applied uniformly across all instances, low-traffic instances can end up growing unnecessarily large right alongside the genuinely hot ones.

Configure conservatively, and asymmetrically on purpose

Scaling up is more urgent and less risky than scaling down — failing to scale up risks real overload and dropped traffic, while overly cautious scale-down just wastes some spare capacity. Most autoscaler implementations are deliberately built this way: quick to react to traffic jumps, slower and more conservative before reducing resources. The chapter's practical recommendation: keep your service comfortably far from key bottlenecks (CPU chief among them), and reserve real spare capacity for both overload protection and basic redundancy — new instances never turn up and start serving instantly, so the autoscaler needs genuine reaction time built into the buffer.

Set hard constraints — because runaway autoscaling is a real failure mode

Two concrete, realistic disaster scenarios the chapter names directly: a buggy new release burns CPU without doing any real work — autoscaler keeps adding capacity in response until all available quota is exhausted, for zero actual benefit. Or: an unrelated dependency starts failing, causing every request to hang indefinitely — autoscaler keeps adding job capacity to handle the growing backlog, which only sends *more* traffic at the already-struggling, unrecovering dependency, making its recovery even less likely.

The fix: set explicit minimum and maximum bounds on what the autoscaler is allowed to do, confirm you actually have enough quota reserved to reach those limits, and treat this as a genuine capacity-planning input, not an afterthought. Equally important: maintain an easy, obvious, fast, well-documented kill switch, and make sure on-call engineers actually know how to disable autoscaling and manually control scale when something is clearly behaving wildly.

Don't let autoscaling silently overload what's downstream

An autoscaler correctly reacting to more traffic passes that increased load straight down the stack — to databases and other backend dependencies that may not scale as gracefully or linearly. A real dependency analysis before deploying autoscaling matters here, ensuring downstream services have genuine headroom and degrade gracefully rather than falling over. This gets trickier still when multiple microservices share a quota pool — one service autoscaling aggressively in response to a spike can starve the others of the same shared quota, especially if the traffic spike affects all of them simultaneously. Splitting quota per microservice (potentially even into separate projects) is one concrete fix.

Balance across regions, not just within one

Some autoscaling systems (AWS, GCP among them) run a separate, continuous rebalancing job across regional instance groups, specifically to avoid one zone growing disproportionately large relative to its siblings. This evens out quota usage where quota is allocated per-zone, and — as a genuine side benefit — spreading instances across more zones also spreads your failure domains, directly improving resilience against a single zone's outage.

case study 2

Dressy: when load balancing and load shedding secretly fight each other

A fictional online dress retailer runs its app across three equally-sized regions specifically to absorb single-zone failures. One day, customer complaints flood in — the app is unreachable for many users. Investigation reveals something genuinely strange: the load balancer is inexplicably funneling all traffic into Region A, even though A is completely overloaded while B and C sit nearly empty.

sketch — how a "successfully rejected" error looked like efficiency to the load balancer (original diagram)

The team's load balancer was utilization-aware, reading each container's CPU usage to estimate how "full" it was. From its perspective, Region A's per-request CPU cost looked ten times lower than B or C — so naturally, it kept routing more traffic there, believing it had found spare, efficient capacity.

The real mechanism: load shedding, deployed independently earlier that week, was quietly lying to the load balancer. Once CPU utilization crossed a threshold, servers in Region A began instantly rejecting new requests with an error rather than processing them — first 10%, then 20%, then 50% — while total CPU usage stayed essentially flat. Every rejected request looked, to the load balancer, exactly like a genuinely cheap, fast, successful response. Region A was "serving" 240 RPS at its 80% CPU shedding cap; B and C were only managing 120 RPS each. The load balancer logically concluded Region A was simply more efficient, and kept sending it more traffic — a positive feedback loop entirely invisible to either system in isolation.

What actually went wrong: load shedding and load balancing were each added separately, likely by different engineers, and nobody had examined the two as one unified traffic-management system. The load balancer had no way to distinguish a fast successful response from a fast rejected one.

The fix: teach the load balancer's utilization calculation that an error response isn't free — count each shed request as, say, 120% CPU utilization (any value clearly over 100% works) instead of near-zero. Region A now correctly reads as overloaded, traffic naturally redistributes to B and C, and the system settles into genuine balance instead of a false, error-driven equilibrium.

combining strategies

Load balancing, autoscaling, and load shedding are never fully independent

Real systems routinely need more than one load-management tool working together — regional autoscaling combined with cross-region load balancing; local-latency-optimized load balancing combined with load shedding for genuine traffic spikes beyond what new capacity can absorb in time; autoscaling combined with load shedding when a data pipeline runs out of memory faster than new pods can be provisioned. Each concrete combination brings its own specific interaction risk worth pre-empting deliberately:

  • Load balancing + autoscaling can form a positive feedback loop — traffic concentrating near one location causes that location to grow, which then attracts even more traffic. If that location later fails, the remaining locations can be caught without enough spare capacity to absorb the overflow, and scaling them up isn't instant. Setting a minimum instance count per location, reserved specifically as failover headroom, guards against this.
  • Autoscaling + load shedding should be sequenced deliberately — thresholds should generally let the system autoscale before load shedding kicks in, or you risk shedding traffic you could have simply scaled up to serve instead.
  • RPC deadlines matter for both together. Without an explicit deadline, a process holds resources for an in-flight request indefinitely (or until a very large default timeout) — quietly risking memory exhaustion and crashes, and inflating latency for users waiting behind it. The chapter's concrete recommendation: servers should actively terminate requests that have run too long, clients should actively cancel requests they no longer need a response to (don't let a server start an expensive operation for a client that already gave up and returned an error to its own user), and a sane default deadline should be documented directly in the API's own interface definition.
The chapter's closing synthesis: load balancing, load shedding, and autoscaling all pursue the same underlying goal — equalizing and stabilizing system load — but because they're so often built, deployed, and configured by different engineers at different times, they end up behaving as if independent when they genuinely aren't. Both the Pokémon GO and Dressy case studies show the same underlying failure shape: individually reasonable systems, each behaving exactly as configured, combining into an emergent, genuinely dangerous feedback loop nobody explicitly designed for. Treating traffic management holistically — instrumenting the intersections between tools, watching explicitly for feedback loops, and coordinating emergency shutdown across every layer — is what actually prevents that outcome, rather than discovering it for the first time in a live postmortem.
